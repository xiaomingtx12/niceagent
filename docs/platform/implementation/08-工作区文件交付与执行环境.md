# 工作区、文件交付与执行环境

[返回模块目录](README.md)

## 工作副本与已保存文件

当前 `/workspace/` 是本轮工作副本，普通文件工具和 Shell 编辑副本不会自动改变平台已保存文件。运行装配创建空的工作副本，不启动就下载全部历史文件。

持久化空间按账号与应用生成稳定 scope ID，可跨会话访问。`workspace_files.conversation_id` 当前存放的是这个派生 scope，不应看到字段名就认定文件仅属于某个真实 Conversation。

| 工具 | 行为 |
| --- | --- |
| `list_saved_files` | 查询已保存文件元数据，不读取全部正文 |
| `load_saved_file` | 加载指定文件至当前副本，并记录真实 revision |
| `deliver_file` | 保存明确指定的产物，成功才返回 saved |
| 原生 write/edit 工具 | 编辑当前副本，不隐式交付 |

这一分离减少了装配时的网络读取和任务结束时的全目录扫描，也避免临时脚本、缓存、中间文件全部成为用户交付物。

## 加载与覆盖的并发控制

`WorkspaceDelivery` 把 revision 绑定到“具体工作副本路径＋保存目标”。重复加载同一来源时复用已加载副本，不从远端覆盖模型刚编辑的内容。

没有加载目标版本时，交付按 expected_revision=0 只允许新增；加载过的文件用真实 revision 更新。另一个会话已经保存新版本时，本次提交冲突，不强行覆盖。

版本不能只绑定原文件名：把新版本加载到另一副本，不应让原来的旧副本获得覆盖权限。

## 对象存储与元数据的提交顺序

`WorkspaceFileStore.write_bytes` 的顺序是：

1. 计算内容摘要，确定覆盖所需的 revision。
2. 使用唯一 object key 上传新对象。
3. Repository 在作用域锁内校验版本、配额和路径，提交新元数据，revision 递增。
4. 元数据失败则尽力删除新对象；提交成功后尽力删除旧对象。

删除则先提交元数据不可见和 revision，再清理对象。这样对象清理失败不会让用户继续从正常元数据查询看到已删除文件。

对象存储与 PostgreSQL 没有分布式原子事务。best-effort 清理失败仍可能留下无引用对象；当前不能描述成已经具有完整异步垃圾回收闭环。

## 执行环境与路径

`AgentRuntimeAssembler` 组合工作副本、只读 Skill、会话归档、可选记忆和执行后端，并明确每项资源的持有与释放责任。后端创建失败也需要清理此前已创建的资源。

Sandbox 工厂按配置选择 Provider，远程 Daytona/LangSmith 后端采用延迟初始化，首次实际需要时才创建资源；可选 SDK 也按 Provider 加载，避免未选中的依赖拖累其他运行方式。

文件工具使用 `/workspace/` 等虚拟路径；Shell 根据执行后端使用实际目录，提示词说明 workspace/、skills/ 等相对路径。不能假定命令字符串里的虚拟绝对路径会自动替换。

本地 Shell、操作系统隔离和远程沙箱的安全能力不同。设置虚拟路径与访问策略不等于主机级进程隔离；部署时需要明确实际选择的 Provider、资源限制和网络能力。

## 技术亮点与排障

- 显式交付使“文件已保存”对应一次可验证工具结果。
- revision 保护内容并发，作用域锁保护配额等聚合约束，唯一对象键避免未提交上传覆盖旧对象。
- 资源生命周期集中管理，区分运行结束释放句柄与删除会话级远程资源。

“写了文件但列表没有”先查是否调用 deliver_file；“覆盖冲突”查加载来源与 revision；“运行完文件消失”区分临时副本与已交付文件；“Shell 找不到路径”查虚拟路径和实际工作目录，不直接改成宿主机任意路径。
