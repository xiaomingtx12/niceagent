# 后台执行、部署与排障

[返回模块目录](README.md)

## 当前任务分配

| 任务 | 执行位置 | 主要事实来源 |
| --- | --- | --- |
| 主 Agent Run | Web 服务进程内的有界 ThreadPoolExecutor | AgentExecution、事件表、checkpoint |
| 本平台异步子 Agent | 内部 HTTP 入口创建另一个 Run，仍进入运行线程池 | 子 Conversation 与 AgentExecution |
| 文档索引、启停、删除任务 | Celery Worker | Document、Segment、向量库 |
| Agent 测评 | Celery Worker | AgentEvaluation 及冻结材料 |
| 实时事件合批写库 | 每个活动执行片段独占写线程 | 事件表及已提交水位 |

配置中的 AGENT_RUN_MAX_WORKERS 默认是 5，并使用同容量 BoundedSemaphore 控制运行名额；提交采用非阻塞获取，容量耗尽走失败处理，不无限排队。仅设置线程数而不限制待执行工作，会把压力藏到无界队列；本平台额外控制名额正是为了避免这一点。

Celery 的 broker_url 和 result_backend 当前都由 Redis 地址及各自 DB 配置构造，默认 DB 均为 1。Redis 队列、Redis 业务缓存和 PostgreSQL 业务结果是不同用途；业务状态不应只依赖 Celery result backend。

## 为什么有线程池并不等于多机调度

本地 Tracker、事件 Hub、取消 Event 和执行容量都属于某个进程。Web 服务扩为多个 worker 后，会出现本机看不到另一个进程执行片段的情况；把它当作孤儿运行会误判。

已有数据库锁和 executor_id 保护写入资格，但它们没有自动提供执行心跳、跨机取消广播或共享实时事件分发。SSE 落到另一进程时也不能直接访问原进程内存尾部。

如果以后把 Run 移到 Celery，需要同时设计：任务认领与租约、过期执行回收、幂等重投、跨进程停止请求、事件通知、Worker 退出和资源释放。单独把 execute 包成 shared_task 不足以完成迁移；带副作用的工具也不能因 Worker 重投就无限重放。

## 主循环与保护上限

DeepAgents 使用模型—工具—模型的图循环，模型不再请求工具时通常自然结束。它不是平台手写的无限 while，也不会只因为还有未完成 todos 就必然继续。

主图当前配置模型调用上限 50、工具调用上限 200，模型与只读工具重试最多 2 次；模型限制采用 end，工具限制采用 continue。图的递归步数、模型调用次数、工具调用次数和跨恢复的业务 Run 总预算是不同概念。

同步子图没有自动继承主图的全部平台中间件，不能把主图限制宣传为所有子 Agent 合计共享的硬预算。执行验收还使用独立的限制配置，见 [测评详解](10-测评证据与用量分析.md)。

## 资源与连接生命周期

线程执行使用各自 Flask 上下文与数据库 Session；不把请求线程的活动 Session 交给后台写线程。模型调用前尽可能结束读取事务，避免长时占用连接。

AgentRuntimeResources 负责本轮资源退出；Sandbox 可能借用工作副本，也可能使用会话级远程资源。释放 Backend 句柄和删除远程沙箱不是同一操作，失败清理需要遵守所有权关系。

业务数据库、LangGraph checkpoint 和 Store 的连接来源应分别观察；应用连接池空闲并不代表框架的持久化连接也空闲。

## 按阶段定位问题

| 现象 | 优先检查 | 不能直接推断 |
| --- | --- | --- |
| 长期“等待模型调用开始” | 运行名额、装配日志、附件/模型客户端/工具/Store 阶段 | 一定是模型首字慢 |
| 模型开始后迟迟无正文 | 请求是否收到 token、工具或摘要调用是否进行中、供应商延迟 | 一定是 SSE 丢事件 |
| 有实时输出，刷新后缺少尾部 | 事件写线程、已提交水位、尾批失败、进程退出 | 已显示就必然落库 |
| 切换页面卡顿 | 浏览器长任务、状态归并、Markdown 与 DOM 布局 | 一定是响应字节数过大 |
| 异步任务一直“已启动” | 子 Run 状态、装配、模型开始事件、观察请求错误 | 已启动意味着正在持续产出 |
| 测评一直排队 | Celery Worker、broker、投递失败、记录截止时间 | 主 Agent 线程池也会处理它 |
| 文件冲突 | scope、加载 revision、目标文件是否被其他会话更新 | 多重试一次就安全 |

日志串联优先使用 app_id、conversation_id、run_id 和相关阶段；模型装配看 agent_assembly_timing，客户端构造看 model_load_timing，首段交付看 agent_delivery_timing。

上述机制没有提供性能提升百分比或生产容量结论。容量还需在实际模型、工具、连接池和部署拓扑下测量；本文只记录实现及排障方法。
