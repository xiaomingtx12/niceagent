# 身份、应用配置与模型装配

[返回模块目录](README.md)

## 职责与关键数据

应用是一份可以编辑和发布的能力定义。运行时装配需要同时回答：使用哪份配置、谁有权使用其中资源、使用哪条模型连接，以及哪些状态属于本次执行。

| 对象 | 当前职责 |
| --- | --- |
| Account | 平台认证身份、资源所有者 |
| End User | 应用范围内的消费者身份，不等于应用所有者 |
| Conversation Owner | 会话访问的稳定归属，不由每次请求重写 |
| AppConfigVersion | 草稿及发布历史 |
| AppConfig | 生产入口引用的配置记录 |
| ApplicationAgentDefinition | 一次加载得到的应用定义及恢复指纹 |
| ProviderApiKey | 账号下的模型连接；同一供应商可有不同连接 |

术语以 [CONTEXT](../../../CONTEXT.md) 为准。不能因为一个账号拥有应用，就认为它是所有外部会话的消费者。

## 配置到运行图的路径

1. Handler 解析可信账号和调用入口，Service 校验应用及会话归属。
2. 定义服务选择草稿、发布配置或内置助手定义；模型选择服务处理默认模型、允许的手动覆盖和失效回退。
3. `AgentFactory.create_executor` 构造本次 AgentConfig，解析模型、已授权工具、知识库、子 Agent 和 Skill。
4. Factory 按需准备附件与文件存储，将配置交给 `AgentRuntimeAssembler`。
5. Assembler 管理本次运行资源，构造后端、持久化、运行上下文和图；执行器负责之后的使用及释放。

恢复时校验定义指纹，避免用已经改变的能力配置盲目接续旧中断。指纹是配置一致性检查，不是用户授权的替代品。

## 模型加载与装配耗时

`LanguageModelService.load_language_model` 先解析并授权连接、规范化模型配置，再创建实际客户端。`model_load_timing` 将配置处理和客户端构造分开；Factory 的 `agent_assembly_timing` 又分别记录 config、model、tools、subagents、skills 和 total 等阶段。

`total` 包含多个阶段，不能把最后一条 graph 耗时当作总耗时，也不能把装配时间解释为供应商生成时间。

Factory 的 `connection_cache` 是一次装配过程内的连接查询复用，键包含账号、供应商和连接标识。它减少父子 Agent 反复读取同一连接的工作，不是跨请求共享整个有状态 Agent 图。共享图会连带共享回调、中间件状态和本轮资源，不能把两种缓存混为一谈。

发布子 Agent 的配置可批量读取；发布子 Agent 使用自己的发布模型，自定义跟随配置按本次父模型解析。这比逐个子 Agent 重走完整应用查询链更容易控制查询次数。

## 发布的实际事务边界

`publish_draft_app_config` 当前依次创建 AppConfig、更新 App 发布指针、重建 Dataset 关联、追加发布历史；调用了多次 `create`、`update` 和 `auto_commit`。

因此，**当前发布并非一次数据库事务原子完成**。中途失败可能留下部分已提交变化；并发发布的版本递增也需要额外关注。把这些步骤合并为明确事务，是后续改进方向，不是现有保证。

发布配置保存能力绑定，并不等于把远端 MCP 服务、知识库索引、模型权重及所有外部工具内容都做了不可变快照。需要完整复现时，应进一步明确这些外部依赖的版本。

## 技术亮点与难点

- 定义读取、模型选择、资源装配分开，减少入口之间各写一套默认模型规则。
- 同一请求内复用查询结果，同时维持账号隔离；性能优化不能扩大缓存的权限作用域。
- 配置 JSON 需要结构校验和引用资源校验，两者缺一不可：字段合法不代表有权使用对应工具。
- 可恢复运行既依赖 checkpoint，也依赖启动与恢复时的配置一致性。
