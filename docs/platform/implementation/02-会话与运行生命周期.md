# 会话与运行生命周期

[返回模块目录](README.md)

## 先区分四个对象

| 对象 | 作用 |
| --- | --- |
| Conversation | 持续会话和访问归属 |
| ConversationTurn | 一次用户问题、最终回答及累计用量 |
| AgentExecution | 这轮任务的启动、等待、恢复、取消和结算 |
| executor_id | 当前执行片段的写入资格；恢复可以更换，Execution ID 不变 |

SSE 连接只是观察通道。关闭连接不能自动代表取消 Execution，重新连接也不应创建另一轮任务。

## 启动与幂等

`start_run` 在授权范围内锁定会话，核对输入消息 ID、输入内容及当前占用，再创建 Turn 和 Execution，事务提交后才提交后台执行。这样后台线程不会先开始调用模型，而创建记录的事务随后失败。

`input_message_id` 承担业务去重：同 ID 同输入返回已有运行，同 ID 不同输入拒绝。commands 外壳的 `id` 仅用于关联响应。前端重新点击发送会产生新消息 ID，不能宣称所有重复点击或网络重试都具备相同幂等效果。

同会话的占用范围包含 `running` 与 `waiting_input`，通过查询锁和数据库约束共同保护。先锁会话、再锁 Run 的顺序应保持一致，避免不同入口逆序拿锁。

## 暂停、恢复与取消

1. 模型调用启用的 `ask_user` 工具后，框架产生中断。
2. 业务结算保存待填写批次和展示状态，Execution 进入 `waiting_input`。
3. `submit_answers` 校验批次、答案、身份和定义指纹，保存 Submission 并分配新的执行片段。
4. 事务提交后通过框架 resume 继续同一 Execution、同一 Turn，不重复插入原始提问。
5. 重复提交相同已接受答案返回原回执；改变已接受答案不能再次恢复图。

取消活动执行先记录停止请求，再通知本地执行器排空；阻塞工具能否快速停下取决于工具实现。没有活动执行线程的待填运行可以直接取消并清除待填写内容。

**已取消的 Run 不可恢复。** 下一条普通提问创建新 Run；关闭或暂不填写表单与取消 Run 是两件事。行为依据见 [最小交互业务约定](../../Agent-最小交互业务约定.md)。

## 执行与结算

后台链路为 `_execute_run → _execute_agent → AgentExecutor.execute`。每个片段拥有自己的资源、取消信号和事件写线程；结算前排空事件尾批。

`_finalize_run` 核对 executor_id 与活动状态，再写入最终结果、状态和用量。旧片段返回、重复结算或失去执行资格的线程不能覆盖较新的运行结果。

`ConversationTurn.apply_usage()` 累计执行片段用量；恢复不是新建一条独立问答，也不是用最后一个模型调用的用量覆盖整轮用量。

## 查询为什么独立

`AgentExecutionQuery.get_state` 用于恢复消息列表、最近运行摘要和待填写状态，不加载全部执行事件。读取采用短只读 `REPEATABLE READ` 事务，避免消息与运行状态来自不同查询时刻。

快照和 SSE 负责具体执行过程；这使初次进入会话不必付出全部历史 token 事件的传输与渲染成本。

## 技术亮点与边界

- Run 身份稳定、执行片段可替换，既支持恢复，也能拒绝迟到线程写入。
- 用户答案作为独立 Submission 保存，恢复去重不依靠扫描展示事件。
- 数据库状态是业务事实，checkpoint 是框架执行状态，进程内 Tracker 是本机存活信息；三者职责不同。
- 当前 Tracker 和取消通知以进程内状态为主。多进程中“本机没有线程”不能直接推导“这个 Run 已死亡”；共享租约是部署改进项。
