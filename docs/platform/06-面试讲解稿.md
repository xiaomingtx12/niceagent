# 面试讲解稿：NiceAgent 平台项目

## 1. 60 秒项目介绍

我参与的是一个 Agent 应用平台。平台允许用户配置并发布 Agent 应用，配置内容包括模型、系统提示词、知识库、工具、工作流、Skill 和长期记忆。用户可以从调试工作台、WebApp 或开放 API 发起任务。后端把每次提问拆成 Conversation、Turn 和 Agent Execution 三层对象，后台用 LangGraph/DeepAgents 执行，过程中产生有序事件，通过 SSE 实时返回，同时把事件、状态、Token 和费用持久化，支持断线续传、表单中断恢复、取消、历史查询和 Agent 测评。

## 2. 业务需求怎么讲

- 对平台管理员：需要创建、编辑、调试、发布和回滚 Agent 应用。
- 对 Agent：需要组合模型、知识、工具和记忆，能够自主执行多步任务。
- 对终端用户：需要在不同入口使用同一应用，并看到流式进度、工具调用和最终结果。
- 对运营和研发：需要追踪每次运行的状态、成本、错误和质量评分。

## 3. 最值得讲的三个实现难点

### 难点一：长任务和流式执行

HTTP 请求不能一直占用线程，因此提交请求只负责创建 Execution，实际执行放到后台。事件使用单调递增 sequence 持久化，SSE 只是实时通知；客户端断线后按 sequence 查询即可恢复。

### 难点二：并发、幂等和状态一致性

启动任务时锁 Conversation 行，配合部分唯一索引保证同一会话不会同时存在两个占用中的 Execution；输入消息作为幂等键，重复提交返回同一个 Execution。状态结算和事件写入放在事务中，提交成功后才通知客户端。

### 难点三：可恢复的人机交互

Agent 需要用户补充信息时，不阻塞线程，而是把待填表单写入 Execution 并进入 `waiting_input`。用户提交答案后记录 Submission，再恢复同一个 Execution。答案提交具有批次幂等，避免重复提交造成两个分支。

## 4. 数据库设计如何讲

核心关系是 `App → Conversation → Turn → Execution → Event`。App 保存配置和发布指针；Conversation 表示持续会话；Turn 保存一轮问答和用量；Execution 保存运行状态、输入中断和恢复信息；Event 保存可重放的执行过程。Dataset、Document、Segment 支撑 RAG，Tool/MCP/Workflow 保存外部能力，Evaluation 保存独立测评快照。

## 5. 为什么采用草稿和发布双配置

调试需要允许修改配置而不影响线上用户，生产运行又必须使用稳定快照，所以草稿和发布分离。发布时生成版本快照并更新 App 指针；Execution 启动时冻结配置指纹，这样线上运行不会被后台编辑影响，也能根据版本追溯回答来源。

## 6. 如果被追问当前不足

当前需要重点关注多进程执行一致性：取消信号和孤儿任务收敛部分依赖进程内 Tracker，扩容到多 Worker 后应改成共享租约、心跳或 Redis 消息；配置 JSONB 需要 schema_version 和迁移器；敏感凭证要加密或哈希；异步任务需要统一 trace_id、重试和死信机制。

## 7. 面试表达顺序

先用一句话说明平台价值，再讲“配置应用—发布—用户提问—Agent 执行—事件返回—结果沉淀”的主链路；然后重点展开 Execution 状态机、事件续传、幂等并发和配置版本；最后补充 Dataset、工具、Workspace、测评和当前工程改进点。
