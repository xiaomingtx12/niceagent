# 业务建模自梳理（以 internal/model 为准）

> 本文按 `internal/model` 的实际 ORM 定义补全。表名、字段名、约束名均取自代码；
> 带「差异」标记的段落是 Model 与迁移/数据库可能不一致之处，只做提示，不作为改动依据。

# ER模型建模基本规则，怎么拆分业务领域，在一个业务领域中去合理的拆分不同表的职责

一个表表示一个相对独立的业务对象，表之间建立关系

是否需要持久化？系统重启、数据重新加载后，这个值是否必须恢复，并且能否可靠地重新计算出来？

- 用户或业务输入的数据
- 业务状态
- 业务事实和历史快照
- 外部系统返回的重要结果
- 审计和追踪信息

通常不需要持久化的字段：

- 可以稳定计算出的字段
- 临时展示字段
- 可由其他字段推导出的重复字段

权衡情况下：有些字段虽然能计算，但计算成本较高，或者需要固定历史结果，这时可以持久化。

## 本项目的落地判据

上面四条规则在本项目里的具体体现，可以直接当作新增表/新增字段时的自检清单：

- **能算出来的不落库**：`Dataset.document_count`、`hit_count`、`character_count`、`related_app_count`，`Document.segment_count`，`Conversation.is_new`，`Account.is_password_set` 都是 `@property` 现算，不是列。
- **算不动或要固定历史才落库**：`Message` 的 `total_token_count` / `input_token_count` / `token_usage` / `model_call_count` / `tool_call_count`，`Document.character_count` / `token_count`，`Segment.hit_count`，`WorkflowResult.latency`。这些要么依赖外部模型返回，要么需要在应用配置被改之后仍保留当时的结论。
- **历史快照独立成表**：`AppConfigVersion`（发布历史）、`AgentRunEvent`（执行过程事件）、`AgentEvaluation.source_snapshot`（测评当时的材料）。改配置不能改写历史结论，所以快照必须和"当前值"分表。
- **外部系统返回的重要结果**：`MCPTool.input_schema` / `raw_definition`（MCP server 发现的工具目录）、`ProviderApiKey.discovered_models`（模型发现结果）。
- **审计与追踪**：各表统一的 `created_at` / `updated_at`，`Message.trace_id`，`AgentRun.executor_id`（执行权标识）与 `cancel_requested_at`。
- **临时/展示态不落库**：工作台流式片段（`AgentRunExecution` 只存在于进程内）、Agent 执行上下文（交给 LangGraph checkpoint，不在关系库）。

## 关系表达方式约定

本项目有两种外键风格，混用是刻意的，选型标准如下：

- **`ForeignKey(...)` 真外键**：仅用于生命周期严格从属、父删子删的场景，目前只有 `AgentRun.message_id → message.id`、`AgentRunSubmission.run_id` 和 `AgentRunEvent.run_id` 指向 `agent_run.id`（均 `ondelete="CASCADE"`）。
- **裸 UUID 列 + 索引 + 注释说明语义**：其余全部关系。原因是跨域解耦（会话/应用/账号可被独立清理）、支持内置助手这类"不要求存在 App 行"的虚拟归属（`Conversation.app_id`、`AgentRun.app_id`、`WorkspaceFile.app_id`），以及避免 ORM 级联把大表一起带走。裸列必须配索引，否则等于没有关系。

# 一、用户账号认证鉴权层

## account（账号表）

平台侧使用者身份，是绝大多数业务表的租户边界（`account_id`）。

| 字段 | 说明 |
| --- | --- |
| `id` UUID PK | `uuid_generate_v4()` |
| `name` / `email` / `avatar` | 展示信息，`account_email_idx` 支持按邮箱查 |
| `password` / `password_salt` | 可空；第三方登录账号不设本地密码，由 `is_password_set` 现算判断 |
| `last_login_at` / `last_login_ip` | 登录审计 |
| `updated_at` / `created_at` | 时间戳 |

设计点：`Account` 同时继承 `UserMixin`，承担 Flask-Login 的登录主体；密码本体与盐值同表但不做派生列。

## account_oauth（第三方授权认证）

`account` 的从属扩展，一个账号可绑定多个 provider。

| 字段 | 说明 |
| --- | --- |
| `account_id` | 归属账号，`account_oauth_account_id_idx` |
| `provider` / `openid` | 联合索引 `account_oauth_openid_provider_idx`，保证按 (openid, provider) 定位 |
| `encrypted_token` | 第三方访问令牌密文，不落明文 |

设计点：OAuth 绑定关系独立成表而不是往 `account` 加列，避免"每接一个渠道加一组列"。

## api_key（API秘钥表）

开放 API 的调用凭证，归属账号。

| 字段 | 说明 |
| --- | --- |
| `account_id` | 归属账号，`api_key_account_id_idx` |
| `api_key` | 加密后的秘钥，`api_key_api_key_idx` 支持按 key 反查 |
| `is_active` | 是否可用；吊销走状态而不是删行 |
| `remark` | 备注 |

## provider_api_key（用户配置的模型提供商连接）

既是"模型层"的凭证，也是本层的鉴权资产。语义已经从"一个 provider 一把 key"升级为**一条服务连接**。

| 字段 | 说明 |
| --- | --- |
| `account_id` + `provider_name` | 联合索引 `provider_api_key_account_provider_idx` |
| `api_key` / `base_url` | 凭证与用户级 OpenAI-compatible 地址（支持第三方中转） |
| `connection_name` | 用户可见的连接名，取代了原来的 `remark` |
| `api_format` | `chat_completions` 或 `responses` |
| `is_active` | 是否启用 |
| `discovered_models` | 最近一次显式发现的模型快照 |
| `enabled_models` | 用户激活使用的模型名列表 |

设计点：这个 `id` 是全平台引用模型连接的标准句柄——`AppConfig.model_config`、`SubAgentConfig.model_connection_id`、`Dataset.embedding_provider_connection_id`、`AgentModelSelection.provider_connection_id` 都指向它，而不是指向"提供商名称"。

# 二、最外层-应用配置装配层

本层回答一个问题：**一个应用"当前长什么样"和"历史发布过什么"要分开存**。

## app（AI应用基础模型类）

应用外壳，只放身份、展示与发布指针，不放任何能力配置。

| 字段 | 说明 |
| --- | --- |
| `account_id` | 应用所有者，`idx_app_account_id`；**不代表应用使用者** |
| `app_config_id` | 已发布的运行时配置；为空表示未发布 |
| `draft_app_config_id` | 草稿配置指针 |
| `name` / `icon` / `description` | 展示信息 |
| `token` | 应用凭证，`app_token_idx`；仅发布状态有效 |
| `status` | `AppStatus`：`draft` / `published` |

只读属性承载了两条业务规则：

- `app_config`：按 `app_config_id` 取运行时配置，未发布返回 `None`。
- `draft_app_config`：按 `(app_id, config_type=draft)` 取草稿，**不存在则用 `DEFAULT_APP_CONFIG` 现场创建一条并提交**——草稿是"懒初始化"的，所以业务代码可以假定它总是存在。
- `token_with_default`：未发布时清空 token；已发布但无 token 时生成 16 位随机串。凭证生命周期跟发布状态绑定，避免"取消发布后旧 token 还能用"。
- `wechat_config`：取微信发布配置，不存在则创建；并会双向校正 `status` 与 `app.status` 的一致性（草稿不允许 configured，已发布且三要素齐全才置 configured）。

## app_config（应用配置模型）

**运行时配置**，一次发布产生一条，被 `app.app_config_id` 指向。

字段分四组：

- 模型与提示词：`model_config`（JSONB）、`preset_prompt`。
- 能力绑定：`skills`（平台内置 Skill 绑定引用）、`subagents`（DeepAgents 同步 sub-agent 团队配置）、`tools`（工具列表）、`workflows`（工作流 id 列表）。
- 检索与记忆：`retrieval_config`、`long_term_memory`。
- 交互与体验：`opening_statement`、`opening_questions`、`user_input`（主 Agent 提问交互）、`speech_to_text`、`text_to_speech`、`suggested_after_answer`、`review_config`。

只读属性 `app_dataset_joins` 提供知识库关联记录。

## app_config_version（应用配置版本历史表）

字段与 `app_config` 基本同构，**额外两个字段承担版本语义**：

| 字段 | 说明 |
| --- | --- |
| `version` | 发布版本号，发布时取 `max(version)+1` |
| `config_type` | `AppConfigType`：`draft` / `published` |

与 `app_config` 的字段差异（这是刻意的，不是遗漏）：

- 有 `datasets`（知识库列表 JSONB），`app_config` 没有，改为落到 `app_dataset_join`。
- `retrieval_config` 默认值不同：`app_config` 是 `'[]'::jsonb`，`app_config_version` 是 `'{}'::jsonb`。

已移除字段：`dialog_round`（上下文轮数）。迁移 `1298e1141878` 建表时在 **`app_config` 与 `app_config_version` 两张表上都建了该列**，代码侧曾存在于两个 Model、`AgentAppConfigReq` / `DraftAppConfigPatchReq`、`DEFAULT_APP_CONFIG`、内置应用模板及其 14 个 YAML 中，但运行时（`internal/core/agent_v2`）从不读取它，属于"存了不用"。现已从 Model 与全部代码引用中移除；**数据库两张表上的列仍在**，需由迁移删除。

设计点：**同一张表同时装草稿和发布历史**，靠 `config_type` 区分。草稿永远只有一条（`draft_app_config` 按 `app_id + draft` 取 `one_or_none`），发布历史按 `version` 递增。这样"草稿"和"版本"共享同一套校验与序列化逻辑，不需要两套 Schema。

`AppConfigVersion` 是 `app_config` 的**字段超集**：发布时把草稿的 `__dict__` 去掉 id/version/config_type/时间戳后直接写进去，因此两个 Model 的字段必须保持同步演进——新增配置项要同时改三处（两个 Model + `DEFAULT_APP_CONFIG`）。

## app_dataset_join（应用知识库关联表）

应用与知识库的多对多关系表。

| 字段 | 说明 |
| --- | --- |
| `app_id` / `dataset_id` | 联合索引 `app_dataset_join_app_id_dataset_id_idx` |

设计点：知识库在草稿/发布配置里以 JSONB 列表存在（`datasets`），但**真正的关联关系落到本表**，因为 `Dataset.related_app_count`、知识库删除前的"是否被应用引用"校验都需要按 `dataset_id` 反查。发布时先删后插（`publish_draft_app_config` 第 4~5 步），取消发布时整体删除。

## 本层的数据流

```
app_config_version(config_type=draft)   --发布-->  app_config        (app.app_config_id 指向)
        ^                                             ^
        |                                             |
   草稿编辑/历史回退                           app_dataset_join
        |                                             |
app_config_version(config_type=published)             |
   (发布时同时落一条, version=max+1)             Dataset
```

- 编辑草稿：`update_draft_app_config` → 只改 draft 行。
- 发布：`publish_draft_app_config` → 新建 `app_config` + 重建 `app_dataset_join` + 落一条 published 版本 + 更新 `app.status` / `app.app_config_id`。
- 回退：`fallback_history_to_draft` → 取某条 published 版本，剔除失效引用后覆盖 draft 行。
- 取消发布：`cancel_publish_app_config` → `status=draft`、`app_config_id=None`、清空 `app_dataset_join`。

# 三、会话层到run层再到事件层面（核心）

本层是整个系统最重的部分，拆成**四个不同生命周期**的对象，边界必须清楚：

| 对象 | 生命周期 | 职责 |
| --- | --- | --- |
| `Conversation` | 长期 | 会话归属与展示信息 |
| `Message` | 一轮 | 一问一答 + 累计用量投影 |
| `AgentRun` | 一次任务 | 执行状态、执行权标识、交互状态 |
| `AgentRunEvent` | 一次任务内递增 | 协议事件流，供重连续传 |
| LangGraph checkpoint | 一次执行 | Agent 真实执行上下文（**不在关系库 Model 中**） |

## conversation（会话表）

| 字段 | 说明 |
| --- | --- |
| `app_id` | 所属应用，`conversation_app_id_idx`；内置助手用固定标识，不要求存在 `App` 行 |
| `name` / `summary` | 名称与会话摘要（供任务检索） |
| `is_pinned` / `is_deleted` | 置顶与软删除 |
| `invoke_from` | 调用来源 |
| `created_by` | **首次创建来源**：调试/任务/助手存 `Account.id`，WebApp/Service API 存 `EndUser.id` |
| `owner_account_id` | **可管理会话的 `Account.id`**，与应用所有者分开；外部渠道及未回填旧记录可为空 |

设计点：`created_by` 与 `owner_account_id` 必须分开。"谁第一个说话"和"谁有权管理这个会话"在外部渠道下不是同一个人。`is_new` 属性按 `Message` 计数现算，不落库。

## message（消息表）

一轮问答的持久化投影，同时是**用量统计的归属地**。

分组看：

- 关联：`app_id`、`conversation_id`、`invoke_from`、`created_by`（本轮发送者，可能与会话 `created_by` 不同）。
- 提问：`query`、`image_urls`、`attachments`（附件元数据）。
- 回答：`answer`。
- 状态：`latency`（各执行片段累计耗时，不含等待用户输入）、`is_deleted`、`status`（`MessageStatus`：`normal`/`stop`/`error`）、`error`（可展示信息，堆栈只进日志）。
- 用量：`total_token_count`、`input_token_count`、`output_token_count`、`cached_token_count`、`reasoning_token_count`、`model_call_count`、`tool_call_count`、`token_usage`（按模型汇总）、`trace_id`、`total_price`。

关键方法 `apply_usage(run_usage, accumulate=...)`：

- `accumulate=False`：单次执行**覆盖**统计（普通应用）。
- `accumulate=True`：工作台按片段**累加**（暂停恢复会把多段用量叠加）。
- `run_usage` 为空时**不覆盖**原有统计；即使本片段没有返回 token，`model_call_count` / `tool_call_count` 仍照实记录。
- 事务与去重由调用方控制，方法本身不提交。

索引 `message_conversation_created_id_idx` 是带 `postgresql_where=is_deleted = false` 的部分索引，对应"会话内历史分页"这个唯一的读取模式。

设计点：`total_price` 是历史遗留列，当前执行链路不再计算费用，但分析接口仍读它，所以保留。

## agent_run（一次用户任务及当前执行段）

身份与状态的唯一来源，`message_id` 上还有 `uq_agent_run_message_id` 保证一轮消息对应一个 Run。

| 字段 | 说明 |
| --- | --- |
| `app_id` / `conversation_id` / `invoke_from` | 归属与入口隔离 |
| `message_id` | 承载本轮问答与用量投影的 `Message.id` |
| `input_message_id` | 对齐客户端消息、历史和时间线；相同标识重复启动时复用 Run |
| `status` | `AgentRunStatus`，**独立于消息展示状态** |
| `invocation_snapshot` | 补充表单后恢复原调用参数，校验配置指纹 |
| `interaction_state` | 待填表单、已确认输入及取消后重新填写的状态 |
| `state_snapshot` | **只保存展示投影**；调用参数、交互规则和图 checkpoint 不写入 |
| `last_event_sequence` | 已持久化事件游标，供流式重连续传 |
| `executor_id` | 本次执行段的标识（**不是账号或进程 ID**），启动/恢复换新，结算清空 |
| `cancel_requested_at` | 收到取消请求的时间；执行线程与状态查询都读它，终态保留原值供追溯 |
| `error_message` | 对外失败原因；成功与取消时为空 |
| `started_at` / `finished_at` | 首次开始执行时间 / 进入终态时间（等待用户输入时不设置） |

七条 CheckConstraint 把生命周期规则写进数据库：

1. `ck_agent_run_status`：状态白名单 `running`/`waiting_input`/`completed`/`failed`/`cancelled`。
2. `ck_agent_run_executor`：`running` 必须有 `executor_id`；其余状态必须为空，旧执行段不得保留写入资格。
3. `ck_agent_run_finished_at`：终态必须有 `finished_at`；非终态必须为空。
4. `ck_agent_run_event_sequence`：`last_event_sequence >= 0`。
5. `ck_agent_run_*_object`：三个 JSONB 字段必须是 object。

索引设计对应三类查询：

- `agent_run_conversation_created_idx`：`(conversation_id, created_at, id)`，按会话列历史与最新 Run，入口隔离作为会话内低基数过滤。
- `agent_run_conversation_occupied_uq`（唯一部分索引，只覆盖 `running`/`waiting_input`）：**一个会话同时只能有一个未结束任务**，同时是孤儿 Run 收敛的扫描入口。
- `agent_run_conversation_input_message_uq`：`input_message_id` 幂等去重。

`public_snapshot` 与 `apply_snapshot` 是一对投影规则：`_INTERACTION_VALUE_KEYS`（`pending_inputs` / `input_history` / `input_recovery`）存在 `interaction_state`，其余公开字段存 `state_snapshot`，调用方只面对 `public_snapshot` 一个视图；`apply_snapshot` 会过滤 `_` 前缀的私有恢复参数，**公开事件不能覆盖私有恢复参数**。

## agent_run_submission（表单提交幂等记录）

| 字段 | 说明 |
| --- | --- |
| 主键 `(run_id, input_batch_id)` | `pk_agent_run_submission_batch` |
| `run_id` | 真外键，`ondelete="CASCADE"` |
| `input_batch_id` | **整批中断 ID 集合的摘要**，不是答案哈希或用户 ID |
| `answers` | 已校验答案 |
| `accepted_sequence` | 接受时的事件序号 |

设计点：主键由中断 ID 集合决定、与答案内容无关，所以同一批表单重复提交只会命中同一条记录，天然幂等；`accepted_sequence` 让重复请求返回首次结果而不是重新执行。批次的摘要算法在 `AgentRunInteraction.input_batch_id`：对中断 ID 排序后 JSON 序列化再 sha256，**答案值和请求键顺序都不影响批次身份**。

## agent_run_event（持久化协议事件）

| 字段 | 说明 |
| --- | --- |
| 主键 `(run_id, sequence)` | `pk_agent_run_event_run_sequence`；`sequence > 0` |
| `run_id` | 真外键，`ondelete="CASCADE"` |
| `payload` | `WorkbenchEvent` 协议载荷，必须是 object |

设计点：事件是**协议投影**而不是原始执行日志。`AgentRunService` 只持久化 `messages` / `values` / `tools` / `lifecycle` / `custom` / `input.requested` 这几类方法，因为历史回放必须包含思考、阶段正文和计划状态，不能只恢复工具与生命周期。`(run_id, sequence)` 同时是主键和续传游标。

## 本层不落库的部分

- **Agent 执行上下文**：交给 LangGraph `PostgresSaver`，表由 LangGraph 自己的 `setup()` 管理（`checkpoints` / `checkpoint_blobs` / `checkpoint_writes` / `checkpoint_migrations`），**不在 SQLAlchemy metadata 中**。对应迁移 `f558918e9bc3`、`1df2bf5b63b9` 都是刻意留空的 no-op。
- **进程内执行片段**：`AgentRunExecution`（dataclass）持有 `run_id` / `executor_id` / `done` / `cancel_requested` / `resume`，是内存态，重启即失。

# 四、Agent层（核心）

Agent 层在本项目里**没有独立的"Agent 表"**。Agent 的装配配置全部落在 `app_config` / `app_config_version` 的 JSONB 字段上，运行时由 `internal/core/agent_v2/assembly` 组装成 LangGraph 图。

## 配置字段的职责边界

| 字段 | 承载内容 | 领域对象 |
| --- | --- | --- |
| `preset_prompt` | 人设与回复逻辑（主 Agent system prompt） | 纯文本 |
| `model_config` | 主 Agent 模型配置 | `AppModelConfigReq` |
| `skills` | 平台内置 Skill 绑定引用（`name`/`version`/`digest`/`enabled`） | `SkillBindingReq` |
| `subagents` | SubAgent 编排配置数组 | `SubAgentConfigList` |
| `tools` | 工具绑定（内置 + API + MCP） | `AppToolBindingListReq` |
| `retrieval_config` | 检索配置 | `RetrievalConfigReq` |
| `long_term_memory` | 长期记忆开关 | `LongTermMemoryConfigReq` |
| `user_input` | 主 Agent 向用户提问的交互开关 | `{"enable": bool}` |

## subagents（SubAgent 编排配置）

`SubAgentConfig`（Pydantic，`extra="forbid"` + `frozen=True`）是本层最重的领域对象，字段分三类：

- 身份与提示：`name`、`description`、`system_prompt`。
- 能力：`tools`、`skills`。
- 执行方式：`mode`（`sync` / `async`）、`source`（`custom` / `published`）、`context_passing`（当前固定 `NONE`）。

`SubAgentConfigList` 额外拒绝同名。校验器把三类互斥约束写成了显式规则：

1. **同步自定义**：必须有 `system_prompt`；`model_mode` 只能是 `inherit` 或 `custom`，`inherit` 时清空 `model` / `model_provider` / `model_connection_id`。
2. **异步**：必须有 `graph_id`；**不允许** `system_prompt` / `tools` / `skills` / 独立模型——异步 SubAgent 是一个远程 Agent Protocol 服务，配置只在远端。
3. **已发布**（`source=published`）：必须有 `published_app_id`；异步已发布会自动补齐 `graph_id = mydify:published:<app_id>`，并校验二者匹配；不允许独立模型覆盖（用其发布模型）。

设计点：`graph_id` 前缀 `mydify:published:` 由 `build_published_graph_id` 统一生成，Model 层不做字符串拼接。

## 长期记忆

**不落关系库**。`internal/core/agent_v2/persistence/agent_memory_repository.py` 把记忆实现为 LangGraph `PostgresStore` 里的文件条目：

- 命名空间：`("mydify", "agent-memory", account_id, app_id)`，隔离身份是 `AgentMemoryIdentity`。
- 虚拟路径：`/memories/`，分类固定为 `preferences`（用户偏好）/ `background`（背景信息）/ `experience`（经验方法）。
- 索引文件 `/memories/.index.md` 是系统文件，**不能成为写入或删除的源/目标**。
- 容量校验（文件数、单文件字节、总字节）在 `validate_agent_memory_scope`，Store 连接错误统一转 `AgentMemoryStorageError`。

差异提示：历史上曾有 `memory_facts` 表（结构化事实）和 `plan` 表（计划步骤），均已删除——`memory_facts` 由迁移 `d_v2_009` 移除，`plan` 由迁移 `b3c416557a96` 移除，`message_agent_thought`（思考过程表）由迁移 `d047d8c510b0` 移除。当前 Model 中确实没有这三张表，这是有意为之：思考过程改为 `AgentRunEvent` 投影，计划状态进入 `AgentRun.state_snapshot`，记忆进入 LangGraph Store。

`internal/service/agent/` 下按职责切分，Run 聚合只有一个写入口：

# 五、workflow层

## workflow（工作流模型）

外壳与配置同表，靠 `graph` / `draft_graph` 两列分离运行时与草稿。

| 字段 | 说明 |
| --- | --- |
| `account_id` | 创建账号，`workflow_account_id_idx` |
| `name` / `icon` / `description` | 展示信息 |
| `tool_call_name` | 作为工具被 Agent 调用时的名字，`workflow_tool_call_name_idx` |
| `graph` | **运行时配置** |
| `draft_graph` | **草稿图配置**，默认 `{"nodes": [], "edges": []}` |
| `is_debug_passed` | 是否调试通过 |
| `status` | `WorkflowStatus`：`draft` / `published` |
| `published_at` | 发布时间 |

设计点：与 `app_config` / `app_config_version` 的分表策略**不同**——工作流把草稿和运行时放在同一行的两个 JSONB 列，因为工作流图是一个整体文档，拆表反而要维护两份几乎相同的行；应用配置则因为需要完整发布历史（可回退、可对比版本号）而选择分表。`tool_call_name` 独立成列而不是埋在 `graph` 里，是为了让"Agent 按名字调用工作流"能走索引。

## workflow_result（工作流存储结果模型）

| 字段 | 说明 |
| --- | --- |
| `app_id` | 调用方应用，可空（为空代表非应用调用） |
| `account_id` | 创建账号 |
| `workflow_id` | 结果关联的工作流 |
| `graph` | 本次运行时的图配置**快照** |
| `state` | 工作流最终状态 |
| `latency` | 总耗时 |
| `status` | `WorkflowResultStatus`：`running` / `succeeded` / `failed` |

设计点：`graph` 在这里是快照而不是引用。工作流定义会被继续编辑，但历史执行结果必须能还原"当时跑的是哪张图"，所以运行时配置要复制一份进来。

# 六、工具扩展层

三类工具来源，三类建模，都通过 `app_config.tools` 绑定到应用。

## api_tool_provider（API工具提供者）

一个 OpenAPI 提供方（一份 `openapi_schema` 派生多个工具）。

| 字段 | 说明 |
| --- | --- |
| `account_id` | 归属账号，`api_tool_provider_account_id_idx` |
| `name` / `icon` / `description` | 展示信息，`api_tool_name_idx` |
| `openapi_schema` | OpenAPI 规范原文（Text） |
| `headers` | 提供方级别的请求头（JSONB 数组） |

`tools` 属性按 `provider_id` 现查子工具。

## api_tool（API工具表）

| 字段 | 说明 |
| --- | --- |
| `provider_id` + `name` | 联合索引 `api_tool_provider_id_name_idx` |
| `url` / `method` | 工具调用地址与路由方法 |
| `parameters` | 工具参数（JSONB 数组） |
| `description` | 工具描述（供模型理解用途） |

设计点：`provider` 与 `tool` 拆表，因为认证信息（`headers`）属于提供方、调用契约（`url`/`method`/`parameters`）属于工具。重新粘贴 OpenAPI schema 时只需重刷工具行，不必重建凭证。

## mcp_server（MCP server provider）

| 字段 | 说明 |
| --- | --- |
| `account_id` + `name` | **唯一**索引 `mcp_server_account_id_name_idx` |
| `transport` | `stdio` / 其他，默认 `stdio` |
| `enabled` | 是否启用 |
| `url` / `command` / `args` | 远端地址或本地命令 |
| `env` / `headers` | 环境变量与请求头 |
| `timeout` | 超时秒数，默认 30 |

## mcp_tool（discovered MCP tool catalog）

| 字段 | 说明 |
| --- | --- |
| `server_id` + `name` | **唯一**索引 `mcp_tool_server_id_name_idx` |
| `input_schema` | 工具入参 schema |
| `raw_definition` | 服务端返回的原始定义 |
| `discovered_at` | 发现时间 |

设计点：MCP 工具是**外部系统发现的结果**，`raw_definition` 保留原文以便排查"服务端改了什么导致行为变化"；两个唯一索引保证同一 server 下工具名不重复，重复发现走 upsert 语义。

# 七、知识库层

## dataset（知识库表）

| 字段 | 说明 |
| --- | --- |
| `account_id` + `name` | 联合索引 `dataset_account_id_name_idx` |
| `icon` / `description` | 展示信息 |
| `embedding_provider` / `embedding_model` | 向量模型标识 |
| `embedding_provider_connection_id` | `ProviderApiKey.id`；**指定向量模型连接，不是提供商名称或模型 ID** |
| `embedding_fingerprint` | 配置指纹 |
| `embedding_dimension` | 向量维度 |

只读属性全部现算，不落库：`document_count`、`hit_count`（`sum(Segment.hit_count)`）、`related_app_count`（`count(AppDatasetJoin)`）、`character_count`（`sum(Document.character_count)`）。`embedding_model_config` 把四个向量相关列打包成字典供下游使用。

设计点：`embedding_fingerprint` + `embedding_dimension` 存在的意义是**防止换模型后静默检索错乱**——换 embedding 模型会让已有向量失去可比性，指纹是校验依据。

## document（文档表）

| 字段 | 说明 |
| --- | --- |
| `account_id` / `dataset_id` | `document_account_id_idx` / `document_dataset_id_idx` |
| `upload_file_id` | 关联 `upload_file` |
| `process_rule_id` | 关联处理规则 |
| `batch` | **处理批次**，`document_batch_idx` |
| `name` / `position` | 名称与排序 |
| `character_count` / `token_count` | 冗余统计（`Dataset.character_count` 依赖它，且计算成本高，故落库） |
| 时间线 | `processing_started_at` → `parsing_completed_at` → `splitting_completed_at` → `indexing_completed_at` → `completed_at`，以及 `stopped_at` |
| `enabled` / `disabled_at` | 启用态与人为禁用时间 |
| `status` | `DocumentStatus`：`waiting`/`parsing`/`splitting`/`indexing`/`completed`/`error` |
| `error` | 错误信息 |

设计点：**阶段时间戳逐段落库**而不是只存一个 `completed_at`，因为处理是异步多阶段的，出问题时需要定位卡在哪一段。`batch` 让一次批量上传的文档可以整体重试或整体回滚。

## segment（片段表）

| 字段 | 说明 |
| --- | --- |
| `account_id` / `dataset_id` / `document_id` | 三级索引，`segment_*_idx` |
| `node_id` | **向量存储中的对象 ID**；关系库片段主键是本表 `id` |
| `position` | 片段在文档中的位置 |
| `content` | 片段正文 |
| `character_count` / `token_count` | 长度统计 |
| `keywords` | 关键词列表（JSONB） |
| `hash` | 内容哈希，用于去重与增量重建 |
| `hit_count` | 命中次数，被 `Dataset.hit_count` / `Document.hit_count` 汇总 |
| 时间线 / `enabled` / `disabled_at` / `error` / `status` | 同 `document`，状态集为 `SegmentStatus`：`waiting`/`indexing`/`completed`/`error` |

设计点：`node_id` 与 `id` 分离。关系库是片段元数据的权威来源，向量库是检索索引；两者用 `node_id` 关联，使得向量库可以整体重建而不影响关系库主键。

## keyword_table（关键词表）

| 字段 | 说明 |
| --- | --- |
| `dataset_id` | `keyword_table_dataset_id_idx` |
| `keyword_table` | 关键词倒排表（JSONB） |

设计点：**一个知识库一行**，整张倒排表作为一个 JSONB 文档。全文检索（`full_text_retriever`）直接读整列，不做行级查询，所以不需要拆成"关键词-片段"关系表。

## dataset_query（知识库查询表）

| 字段 | 说明 |
| --- | --- |
| `dataset_id` | `dataset_query_dataset_id_idx` |
| `query` | 查询语句 |
| `source` | 来源，默认 `HitTesting`；枚举 `RetrievalSource`：`hit_testing` / `app` |
| `source_app_id` | 发起检索的应用，非应用调用可为空 |
| `created_by` | 当前检索服务传入的 `Account.id`，**不是 `EndUser.id`** |

设计点：这是审计表，记录"谁在什么时候用什么 query 查了哪个库"，用于命中测试与检索质量分析。

## process_rule（文档处理规则表）

| 字段 | 说明 |
| --- | --- |
| `account_id` / `dataset_id` | `process_rule_*_idx` |
| `mode` | `ProcessType`：`automatic` / `custom` |
| `rule` | 规则详情（JSONB） |

`DEFAULT_PROCESS_RULE` 定义了自定义模式的默认内容：`pre_process_rules`（去多余空白、去 URL 和邮箱）+ `segment`（分隔符序列、`chunk_size=500`、`chunk_overlap=50`）。

设计点：`mode` 独立成列而不是埋在 `rule` 里，因为"自动/自定义"是列表页要展示和筛选的属性。

## 知识库层的处理链路

```
UploadFile --+
             +--> Document --(process_rule_id)--> ProcessRule
Dataset -----+         |
             |         +--> Segment --(node_id)--> 向量库
             +--> KeywordTable (整库一行)
             +--> DatasetQuery  (检索审计)
```

# 八、模型层

模型层没有独立表，由三个部分共同构成：

1. **凭证与服务连接**：`provider_api_key`（见第一章）。`provider_name` + `base_url` + `api_format` + `is_active` 定义一条可用连接，`id` 是全平台引用模型连接的标准句柄。
2. **模型发现快照**：`provider_api_key.discovered_models`（最近一次显式发现的结果）与 `enabled_models`（用户激活使用的子集）。发现结果是外部系统返回的重要结果，必须落库——否则每次都要重新探测远端。
3. **模型配置的持久化位置**：`AppConfig.model_config` / `AppConfigVersion.model_config` / `Workflow.graph` 内的 `model_config` / `SubAgentConfig.model` 系列字段。它们**只存引用**（provider + model + connection_id），不存凭证。

`internal/core/language_model/` 与 `internal/service/language_model/` 负责把"引用"解析成真实客户端。`language_model_service` 的职责边界很清晰：按 `account_id` + `provider_name` + `provider_connection_id` 查 `ProviderApiKey`，校验归属与启用状态，然后组装模型实体。

`AgentModelSelection`（`internal/entity/agent_run_entity.py`）体现了本层的安全边界：`extra="forbid"` + `frozen=True`，字段只有 `provider` / `model` / `provider_connection_id`，注释明确写着"**仅允许引用模型，不接受客户端传入凭证、地址或任意参数**"。客户端永远不能直接传 base_url 或 api_key。

差异提示：历史上存在 `system_model_config` 表（系统级模型配置），相关迁移为 `223e8bdd31a6` / `6837222596d1` / `aece083742e1`，当前 Model 中已无此表，模型配置完全由用户级 `provider_api_key` 承担。

# 九、终端用户使用层

## end_user（应用内使用者身份）

| 字段 | 说明 |
| --- | --- |
| `app_id` | `App.id`；**用户身份只在该应用内有效** |
| `account_id` | 使用者的 `Account.id`；WebApp 由登录身份确定，OpenAPI/微信未绑定账号时为空 |
| `(app_id, account_id)` | 唯一索引 `uq_end_user_app_account` |

设计点：`EndUser` 是"应用内的使用者"，与 `Account`（平台侧使用者）是两个不同身份。`app_id` 上的唯一约束保证同一账号在同一应用内只有一个终端用户记录；`account_id` 可空让匿名渠道（OpenAPI / 微信）也能有稳定的使用者身份。

这个 `id` 是会话与消息里 `created_by` 的两种取值之一——`Conversation.created_by` 注释明确写了"调试/任务/助手存 `Account.id`，WebApp/Service API 存 `EndUser.id`"。读 `created_by` 时必须结合 `invoke_from` 判断是哪一种。

## wechat_config（Agent微信配置信息）

| 字段 | 说明 |
| --- | --- |
| `app_id` | `wechat_config_app_id_idx` |
| `wechat_app_id` / `wechat_app_secret` / `wechat_token` | 公众号开发者 id、密钥、校验凭证 |
| `status` | `WechatConfigStatus`：`configured` / `unconfigured` |

设计点：`status` 不是用户直接设置的，而是由 `App.wechat_config` 属性按"三要素是否齐全"与"应用是否已发布"双向校正。这是一个典型的"可推导但故意落库"字段——推导逻辑跨两张表且需要频繁读取，落库并集中在一处维护比每次查询现算更可控。

## wechat_end_user（微信公众号与终端用户标识关联表）

| 字段 | 说明 |
| --- | --- |
| `openid` + `app_id` | 联合索引 `wechat_end_user_openid_app_id_idx` |
| `end_user_id` | 关联的终端用户 |

设计点：`openid` 是渠道侧标识，`end_user_id` 是平台侧身份。加一层映射表，使得换渠道或换公众号不影响 `EndUser` 与历史会话。

## wechat_message（微信公众号消息模型）

| 字段 | 说明 |
| --- | --- |
| `wechat_end_user_id` | `wechat_message_wechat_end_user_id_idx` |
| `message_id` | 关联的消息 |
| `is_pushed` | 是否推送，默认 `false` |

设计点：这张表记录的是**未推送/待推送的消息**，是渠道侧的投递状态，与 `Message`（业务消息本体）分离。微信有被动回复时限，超时后需要主动推送，`is_pushed` 就是这个补偿链路的游标。

# 十、任务测评层

## agent_evaluation（历史任务测评记录）

| 字段 | 说明 |
| --- | --- |
| `id` | 主键，`uuid_generate_v4()` |
| `account_id` | 发起并拥有此次测评的 `Account.id` |
| `app_id` | 被测应用的 `App.id` |
| `run_id` | 来源 `AgentRun.id`；**测评自身身份是本表 id** |
| `source_snapshot` | 评分时实际使用的材料快照 |
| `criteria` | 评分标准 |
| `judge_config` | 裁判模型配置 |
| `evaluator_version` | 评测器版本 |
| `status` | 状态（`queued` / `running` / 终态） |
| `result` | 评分结果，可空 |
| `error_message` | 错误信息 |
| `created_at` / `finished_at` | 时间线；`finished_at` 可空（排队中未结束） |
| 索引 | `agent_evaluation_owner_app_created_idx`：`(account_id, app_id, created_at, id)` |

设计点：`run_id` 是**来源**而非身份。同一 Run 可以用不同 `criteria` / `judge_config` 多次测评，所以测评 ID 由 `uuid5(NAMESPACE_URL, f"evaluation:{account_id}:{app_id}:{request_id}")` 派生，实现"同一 `request_id` 重复提交返回同一条"。服务里 `_reuse` 会比对 `run_id` / `criteria` / `judge_config` 是否与已有记录一致，不一致才新建。

`source_snapshot` 是本章最重要的一列：它固定了"当时用的是哪份材料、哪个执行结果"。**后续修改应用不改写历史结论**，所以快照必须落库而不是运行时重新拉取。

评测执行本身用 `InMemorySaver` 作为 checkpointer（`agent_evaluation_runtime.py`），因为评测是一次性任务，不需要跨进程恢复。
