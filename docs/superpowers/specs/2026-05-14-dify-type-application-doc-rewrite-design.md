# Dify 型应用沉淀文档重写设计

## 背景

我要优化 `docs/application-notes/dify-type-application/` 这一组应用沉淀文档。

这次不是做轻微润色，而是做一轮中度重写：

- 全部改成作者第一人称
- 删除第三人称和空话
- 压缩宣传式表达
- 强化工程判断、实现边界、状态流和复用价值
- 用少量结构图和流程图替代纯文字堆叠

这组文档的主要读者优先级已经确定：

1. 我自己后续复盘和复用
2. 有一定技术背景的开发者读者

这意味着文档首先要对我自己有用，其次才是对外可读。

## 目标

这轮改写要同时达到下面几个目标：

1. 让这组文档从“能读”变成“能复用”
2. 让每篇文档都先表达我的工程判断，再解释支撑这个判断的实现证据
3. 让整组文档形成清楚的阅读顺序，而不是一组并列页面
4. 让图示承担结构解释职责，而不是装饰页面
5. 让代码片段只保留证据价值，不再喧宾夺主

## 非目标

这次不做下面几类事情：

- 不重命名现有文件
- 不重做整组目录结构
- 不把它改写成面对外部宣传的项目介绍
- 不追求面面俱到的教程化讲解
- 不为了加图而引入额外图片资源文件

## 读者定位

### 第一优先级：我自己复盘

我以后回头看这些文档时，最想快速找回的是：

- 这个模块为什么要这样拆
- 它真正值钱的工程机制是什么
- 哪些状态和运行流最关键
- 哪些地方最容易被高估
- 下次我再做类似系统时，哪些做法值得直接复用

### 第二优先级：有技术背景的读者

这部分读者不需要被普及基础概念，更需要看到：

- 关键边界怎么划
- 真正的实现难点是什么
- 为什么我这样判断，而不是那样判断

## 统一写法

### 写作口吻

所有页面统一改成作者第一人称。

我要主动删除下面这些口吻：

- “作者认为”
- “本文将”
- “该平台”
- “这个项目表明”
- 旁观式总结语气

我要保留的是“我怎么拆、我怎么判断、我为什么这样判断”。

### 统一骨架

除了索引页和写作约束页，每篇正文尽量遵守下面这套骨架：

1. 开头先给判断
2. 说明我为什么单独拆这一层
3. 按真实工程问题往下拆
4. 用少量关键代码片段证明判断
5. 收束到“我现在的判断”或“最值得复用的地方”

### 内容取舍

我会主动删掉这些内容：

- 没有信息增量的过渡句
- 重复表达同一个观点的段落
- “功能很多”“能力很强”这类空泛描述
- 没有实现路径支撑的概念解释
- 外部宣传式表达

我会主动保留这些内容：

- 模块边界
- 关键状态
- 数据流和运行流
- 工程代价
- 容易被低估或讲浅的点
- 后续复用时最值得抄走的机制

### 代码片段规则

代码不是为了展示覆盖率，而是为了当证据。

保留代码片段时遵守下面规则：

- 每段代码只服务一个明确判断
- 优先保留装配点、边界点、状态点、协议点
- 尽量缩短过长代码段
- 代码前后要说明“这段代码证明了什么”

### 图示规则

我会优先使用仓库里已经支持的 `mermaid`。

图示规则如下：

- 每篇控制在 1 到 2 张图
- 图只解释结构、状态、流程
- 不做装饰图
- 不额外引入图片资源文件
- 图不能把正文原样重复一遍

## 验收标准

改完后，我会按下面几条自查：

1. 每篇开头能不能一句话说清我为什么拆这一层
2. 每篇有没有明显第三人称和宣传式表达残留
3. 每篇有没有至少一个可复用的工程判断
4. 图有没有真正帮助理解结构和流程
5. 代码片段是不是只保留了证据价值
6. 整组文档串起来后，阅读顺序和层次是不是更清楚

## 风险与处理

### 风险 1：改写过头，丢掉原文信息

处理方式：

- 保留每篇主题不变
- 保留关键代码证据
- 不改文件名和文档归属

### 风险 2：加图后反而喧宾夺主

处理方式：

- 控制图数量
- 图只解释结构、状态和流程
- 图不能替代正文判断

### 风险 3：不同页面之间边界再次混掉

处理方式：

- Agent 负责会话记忆和事件流
- RAG 负责知识生产链和检索消费链
- LangChain 负责组件协议
- LangGraph 负责编排骨架
- 整体架构页只负责收束主线

## 交付方式

这次先交付规格文档，等用户确认后再进入实际改文阶段。

实际改文阶段的目标不是“逐句润色”，而是按这份规格把整组文档重写成一套更适合复盘和复用的工程笔记。
