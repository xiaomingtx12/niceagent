# 上下文工程与长期记忆：面试准备

## 简历主张与编写思路

按「怎样装配 → 增长后怎样控制 → 跨会话怎样保留」展开。动静分离属于请求组织，摘要与归档属于当前上下文管理，长期记忆属于持久化信息复用，三个层次都应能讲清。

## 一分钟口述

我在装配阶段把稳定业务规则放在提示词前部，应用定义和可选能力规则随后加入，本轮规划选项仅随新的 HumanMessage 注入一次，恢复只传答案。Skills 元数据稳定排序，异步工具说明避免重复追加。容量上根据模型窗口和输出预留配置预算，复用 DeepAgents 的自动及主动压缩，并将历史和大工具结果归档。长期记忆按账号与应用存为 Store 文件，Agent 使用文件工具按需查找读写，不每轮全量注入；写入由容量校验和事务保护，管理接口用内容摘要检查旧版本覆盖。

## 动静分离具体怎么做

| 信息 | 进入上下文的方式 | 原因 |
| --- | --- | --- |
| 进度、文件、规划等固定规则 | 构图时放在稳定前缀。 | 不让时间戳和本轮选项改变固定部分。 |
| 应用名称、说明、业务指令 | 固定规则之后按当前定义装配。 | 应用变化仍有明确位置，不影响前部固定规则。 |
| 异步工具说明 | 复用框架生成文本，提前装配，关闭重复追加。 | 同时供预算观测使用，避免多份相同规则。 |
| Skill 元数据 | 按名称和路径稳定排序，授权变化时刷新。 | 避免仅枚举顺序变化导致请求差异。 |
| 本轮规划偏好 | 新 HumanMessage 中注入一次。 | 不变成跨轮 system 规则；恢复不重发输入。 |
| 用户表单答案 | 通过恢复产生对应 ToolMessage。 | 保持原始工具交互位置，不前置重复汇总。 |
| 长期记忆和归档 | ls/glob/grep/read_file 等工具按需读取。 | 不默认把全部历史和记忆塞进模型输入。 |

前缀稳定有利于供应商缓存复用，但实际命中还依赖工具定义、框架追加文本和供应商门槛。当前没有提供缓存命中率提升的实测结论。

## 预算、压缩与归档

context_budget 按模型窗口和输出预留复制模型 profile，供框架自动压缩和主动 compact_conversation 共用。ContextWindowMiddleware 负责观测和通知，不是摘要算法实现。

摘要减少活跃上下文体积，但会损失细节。归档把历史及大工具结果保留为可读文件，在 /conversation_history/ 和 /large_tool_results/ 下按会话、分支作用域隔离，并限制容量。模型只能读取归档；文本归档不保证所有媒体都能完整重建。

默认窗口或输出预留来自平台配置，不能作为任意供应商模型真实支持容量的证明。模型实际 Token 序列化也可能与平台估算不同。

## 四种存储不要混淆

| 类型 | 保存什么 | 主要用途 |
| --- | --- | --- |
| Checkpoint | 图执行状态和中断信息。 | 多轮执行及暂停恢复。 |
| 摘要与会话归档 | 历史对话及大工具结果。 | 控制当前上下文、查回历史。 |
| 长期记忆 | /memories/ 下分类 Markdown。 | 跨会话复用偏好和项目背景等信息。 |
| 知识库 | 上传文档、分段和检索索引。 | 根据查询召回外部资料。 |

长期记忆是同一账号、同一应用下跨会话共享的文件数据，不是每个会话一份。记忆开关决定是否挂载记忆路由，不取消历史归档所需的 Store。

## 共享记忆怎样处理并发

模型编辑在作用域事务内完成读取、替换、容量校验和写回。管理接口支持 expected_sha256，检测页面加载后内容已被其他会话修改的情况。相同路径、相同正文不会无意义更新时间和发布变更通知。

修改成功后发布 memory_file_update，但文件提交与通知持久化并非同一个事务。另一会话在下一次实际读文件时看到新内容，已经进入上下文的旧 ToolMessage 不会自动替换。

## 典型追问与回答要点

**为什么不自动把全部记忆注入 system？**

记忆越多，固定开销越大，还可能带入与当前任务无关的信息。按需访问让 Agent 先定位再读正文。必须每轮生效的行为应进入应用指令，不能依赖模型每轮自觉读取某个记忆文件。

**为什么不能只截断旧消息？**

可能丢掉任务约束、工具调用配对和关键事实。当前复用框架摘要并保留归档读取入口，仍需承认摘要不保证无损。

**会不会每轮重新注入规划模式？**

新一轮按本轮输入注入一次，表单恢复使用 Command(resume) 而不再插入 HumanMessage。模型公开输出前移除内部选项，业务用户原文保持独立。

**记忆删除后是否完全消失？**

删除 Store 文件不等于删除所有已存在历史消息和摘要中的相关内容。不要把文件删除宣传为全系统历史擦除。

**如何验证动静分离有收益？**

先检查相同配置下请求前缀是否稳定，再在相同模型和负载下观察 cached tokens、输入 Token、首字延迟。没有对照数据时只陈述设计目的。

## 场景推演

会话 A 写入「报告使用中文」，会话 B 的当前上下文已经读过旧记忆。B 不会自动变更已读内容，只有再次读取才看到新版本。若要求马上影响每一轮，应该修改应用指令，而不是用事件通知冒充上下文更新。

## 面试前准备

准备一次主动压缩、一次按需读取长期记忆、一次两个编辑者产生摘要冲突的演示。分别解释界面上的预算估计、模型实际用量及缓存用量，不把三者混为一谈。
