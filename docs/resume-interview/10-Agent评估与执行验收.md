# Agent 评估与执行验收：面试准备

## 简历主张与编写思路

本模块主要是「基于 Rubric 的 LLM-as-a-Judge，结合确定性规则核验」。按评估对象、冻结材料、裁判和规则、修订与证据一致性展开。历史评分与执行验收职责不同，不能笼统说所有评分都重新执行生产任务。

## 一分钟口述

平台提供历史回答评分和隔离执行验收。提交时先冻结任务、标准及相关模型配置，再交 Celery 后台执行。历史评分只读取本轮任务和最终回答，裁判逐项评分并引用原文，证据不足允许弃评。执行验收使用独立图和临时文本文件空间，由 LLM 裁判判断语义标准，程序检查指定文本、文件存在和 JSON 字段，复用 Rubric 的有限评分修订循环。每轮候选内容和证据绑定哈希，最终检查交付内容是否仍是最后被验证的版本。后台通过幂等、原子认领和截止时间保护，避免重复执行和迟到写入。

## 两种模式

| 维度 | 历史评分 | 隔离执行验收 |
| --- | --- | --- |
| 输入 | 已保存的本轮任务与最终回答。 | 冻结任务及草稿执行配置、标准和规则。 |
| 是否生成新内容 | 否。 | 是，在独立执行图中生成并修订。 |
| 判断方式 | 裁判按标准评分，核对覆盖和引用。 | 裁判判断语义，程序核验候选，再结合反馈修订。 |
| 结果 | 分项结论、依据、可评/不可评情况。 | 逐轮候选证据与最终 accepted 状态。 |
| 隔离边界 | 不读取未提供的历史工具轨迹或外部事实。 | 不使用生产工具和长期记忆。 |

它属于推理阶段的输出评估与反馈修订，不更新模型参数，也不是完整覆盖真实外部副作用的端到端生产 Agent 基准。

## 后台处理链路

1. submit 校验应用和源运行授权，从服务端读取材料，冻结标准、裁判配置及执行模式相关配置。
2. 幂等 ID 按账号、应用与请求标识生成。重试核对原请求，不能借用同一个键修改标准或模型。
3. 保存评估记录后投递记录 ID，HTTP 不等待模型评分完成。
4. process 先收敛过期记录，再通过条件更新认领 queued 任务，重复投递不会再次运行。
5. 加载已授权模型后结束读取事务，再进行耗时评分或隔离执行。
6. 保存进度和报告时同时检查 running 与截止时间，迟到结果不能覆盖既有终态。

当前截止时间为提交后 15 分钟，在认领、进度、完成及查询时检查；它不会主动中断正在阻塞的模型调用，Worker 还依赖 Celery 软硬超时。任务 completed 表示报告生成完毕，不表示业务验收通过。

## LLM 裁判和程序检查怎样配合

| 判断 | 适用要求 | 边界 |
| --- | --- | --- |
| 裁判逐项评分 | 内容完整、论证合理、符合任务要求。 | 模型可能偏差，需明确标准、核对引用和覆盖。 |
| contains | 原文包含指定子串。 | 不证明事实正确，也不自动理解同义词。 |
| file_exists | 指定虚拟文本文件存在且非空白。 | 不证明文件内容满足语义要求。 |
| json_keys | 完整 JSON 对象含指定顶层字段。 | 不等于验证所有字段类型、业务逻辑或嵌套结构。 |

没有附加程序规则时，程序检查全部通过也不能直接认定任务通过，仍需裁判判断语义标准。

## Rubric 修订与候选证据

1. 独立图生成候选回答和虚拟文本文件。
2. 开始评分轮次时冻结候选、计算内容哈希并清空旧证据。
3. 检查工具针对该候选产生程序证据，裁判按 Rubric 给出逐项结果。
4. 若未通过且仍有轮次，框架根据反馈继续修订；平台保存每轮进度。
5. 最终验收要求末轮通过、最终回答非空、候选/证据哈希与最终内容一致、程序检查通过。

原生 Rubric 负责评分修订循环；平台负责工具访问限制、候选提取、规则取证、回调适配及最终一致性核验。

例如第一轮 JSON 含 name 和 price，检查通过；第二轮删除了 price，但仍想使用第一轮证据。内容哈希变化使证据失配，不能将旧通过结论套到新产物。哈希只检查内容身份，不证明内容质量。

## 候选提取与证据范围

只取当前轮最近的不带工具调用的最终回答，不回退旧回答。隔离文件使用 StateBackend v2，只接受图内生成的 UTF-8 文本，不读取主机文件。当前限制包括回答 48,000 字符、最多 50 个文件且文件合计 96,000 字符；超限终止而不裁剪后冒充完整评估。

这些是代码边界，不代表通过率或业务容量指标。执行验收没有使用真实生产工具，因此不能证明邮件实际发送、数据库实际修改等外部动作成功。

## 典型追问与回答要点

**为什么冻结材料？**

提交后用户可能修改应用指令、模型或评分标准。报告需要保留当时依据。冻结提高可追溯性，但模型随机性和供应商变化仍使重复评分不保证完全相同。

**LLM 裁判可靠吗？**

它能处理语义要求，但有偏差和不确定性。明确标准、引用校验、不可评标记和确定性检查提供约束。进一步可以做人工标注集与裁判一致性比较，这是后续验证方案，不是现有结论。

**为什么允许弃评？**

历史评分只有任务和回答。若要求判断工具是否真实执行或附件事实是否准确，材料不够时应明确不可评，不能以表达流畅代替真实完成。

**为什么要限制迭代轮数？**

防止修订无限增长成本和耗时。max_iterations 包含第一次评分；内部 iteration 从 0 计数，页面再转为人类轮数。

**一个任务报告 completed，是不是验收通过？**

不是。completed 是后台任务状态；历史看 outcome，执行验收看 accepted。评分失败、任务失败和验收不通过是不同概念。

**评估会影响生产对话吗？**

保存独立记录，使用冻结材料和隔离图；不会把修订结果偷偷写回原生产回答。再次评估是另一份报告。

## 面试前准备

准备一份证据不足而弃评的历史回答，以及一份缺少 JSON 字段后修订的隔离任务。展示逐轮候选哈希、检查结果和最终 accepted，说明为什么报告完成与通过分开。
