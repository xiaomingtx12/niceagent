# NiceAgent 平台生产化架构演进

## 1. 结论与范围

当前平台已经具备任务状态、数据库互斥、提交幂等、Checkpoint、事件持久化、资源清理、权限和限流等基础能力。生产化的重点是明确并验证失败语义，补齐可靠投递和清理补偿，再按容量需要将进程内协调改为多实例协调。

建议分三步：**受控单实例上线 → 异步任务可靠性补齐 → Agent Worker 与共享事件通道**。不需要一开始同时引入 RabbitMQ、Kafka、微服务和 Kubernetes，也不需要把每次工具调用改成 MQ 消息。

本文依据 2026-09-16 工作区实现和现有实现文档整理，属于演进方案。没有执行压测、故障注入、数据库迁移或部署修改。明确的当前行为附有代码入口；监控、备份、基础设施高可用等部署能力未审计，写作口径是“上线需确认或补齐”，不推断线上一定不存在。

以下“验收”均是未来实施时的验证要求，本次仅编写文档。新增状态、字段和业务行为属于建议，实施时还需对齐 [Agent 最小交互业务约定](../Agent-最小交互业务约定.md) 与 [会话执行表定义](../Agent-会话与执行表定案.md)。

## 2. 当前架构事实

| 模块 | 当前实现 | 已有保护 | 主要边界 |
| --- | --- | --- | --- |
| 主 Agent、内部异步子 Agent | API 进程内有界 ThreadPoolExecutor。 | 运行槽位、会话行锁、占用唯一约束、executor_id。 | 本地 Tracker、取消 Event、容量与进程绑定。 |
| 实时事件 | 进程内 EventHub + 每个执行片段写线程。 | 有界背压、批量落库、游标、历史快照、提交后终态。 | 实时尾部可领先持久化；依赖单 API Worker。 |
| 文档处理、评估、辅助生成 | Celery，Redis 作为 broker；结果业务状态保存在数据库。 | 评估已有幂等提交、原子认领、截止时间和冻结材料。 | 业务保存与投递并非一个事务，各任务重试语义不同。 |
| 图状态与长期记忆 | PostgreSQL Checkpointer/Store，另有业务数据库状态。 | 持久化连接管理、状态恢复、记忆作用域与事务。 | 图状态和业务终态不是一份原子快照；临时文件不在 Checkpoint。 |
| 文件交付 | 临时副本 + COS 正文 + SQL 元数据/版本。 | 显式交付、乐观版本校验、失败补偿删除。 | 删除失败主要记日志；跨系统没有原子事务。 |
| 沙箱 | 多 Provider、远程懒初始化；Daytona 会话池。 | 独占租约、TTL、代际、只读 Skill、统一清理。 | 池和定时器在本地；异常退出与远端清理需兜底。 |
| 模型调用 | 中间件重试与次数限制。 | 主图调用上限、只读工具有限重试。 | 不是主子 Agent、跨恢复共享的业务总预算。 |
| 限流与观测 | Redis 限流、阶段日志、Callback 用量统计。 | 账号等范围限流能力、Token 与调用计数。 | 实际路由覆盖需核对；限流存储故障有放行路径；不是完整调用链追踪。 |

当前不能通过简单增加 Gunicorn worker 数扩容。尤其 `_settle_orphan_runs` 依据本进程存活集合收敛任务，多进程时可能把其他进程的运行误判为失联。

## 3. 先确定生产目标，再选择架构

### 场景 A：小规模受控服务

可以继续保持单 API Worker 和有界执行池。需要明确容量、过载拒绝、重启期间的任务处理、备份、清理和告警。接受“运行中进程失效后任务失败，用户可重新发起”的产品语义时，不必立即做自动接管。

### 场景 B：多实例、长任务和独立扩容

需要将执行从 API 分离，并同时实现执行租约、跨进程取消、共享事件分发、检查点写入保护和资源归属。持久化队列只是其中一部分。

### 上线前填写的目标

| 目标 | 应明确的问题 |
| --- | --- |
| 并发与公平性 | 总运行数、每账号/应用运行数、单用户是否可占满容量。 |
| 等待时间 | 是否允许排队、最长排队时长、到期如何告知用户。 |
| 执行时限 | 单次工具、模型请求、执行片段与整个业务任务各自的期限。 |
| 数据恢复 | 业务记录、事件尾部、文件和索引分别允许多大恢复点损失。 |
| 故障恢复 | 哪些任务允许自动重试，哪些必须失败或等待人工确认。 |
| 成本 | 单任务及账号预算如何限制，未知用量如何记录。 |

这些是需要确定的目标，不是平台已经达到的 SLA；具体数值由业务要求与实测容量决定。

## 4. 优先改造总表

| 项目 | 为什么要改 | 怎么改 | 实施条件 |
| --- | --- | --- | --- |
| 任务可靠投递 | 数据库提交后进程退出，任务可能未入队。 | Outbox、幂等消费、投递与业务结果对账。 | 已有 Celery 链路优先。 |
| 清理补偿 | COS/沙箱删除失败可能残留。 | 持久化清理任务、重试、定期巡检。 | 单实例也有价值。 |
| 超时与预算 | 局部调用限制不代表整轮成本可控。 | 分层 deadline、总预算、供应商配额与租户准入。 | 对外服务前明确策略。 |
| 数据备份与可恢复性 | 有持久化不等于备份可用。 | 恢复演练、配置/密钥/文件清单与索引重建。 | 上线基本要求。 |
| 执行 Worker 化 | API 与模型长任务争用资源、进程故障中断任务。 | 队列、持久化认领、租约与受控恢复。 | 多实例或独立扩容时。 |
| 共享事件与取消 | 本地缓冲和信号跨进程不可见。 | 持久化事件边界、共享通知、DB 取消状态。 | 与 Worker 化一起改。 |
| 数据与协议版本 | 发布时旧任务可能无法被新运行时解释。 | 版本标识、兼容期、灰度、排空和回退。 | 长任务与持续发布时。 |
| 可观测与容量验证 | 当前日志能排障，但不能自动量化容量和故障。 | 指标、告警、关联日志、负载与故障演练。 | 各阶段持续补齐。 |

## 5. 已有 Celery 链路：可靠投递与消费

### 5.1 当前问题

评估在保存记录后调用 `apply_async`；文档创建后调用 `.delay()`。评估能捕获投递异常并保存失败状态，但无法覆盖“已提交数据库、进程突然退出、尚未投递”的所有窗口。也可能出现消息已到 broker，但客户端未收到投递确认的模糊结果。

### 5.2 推荐 Outbox 方案

事务发件箱（Outbox）是在同一数据库事务中记录业务变更与待发送意图，后台再可靠投递。

1. 同一事务创建业务记录与 outbox 记录。消息只携带资源 ID、操作类型和版本，避免序列化凭据、ORM Session 或完整大文件。
2. Relay 分批认领 outbox。可用短事务与 `FOR UPDATE SKIP LOCKED` 取得发送租约，再在事务外执行网络发布。
3. 发布成功更新投递状态；失败记录 attempts、next_attempt_at 和脱敏错误。Relay 崩溃后租约到期可重试。
4. 发送成功但状态未更新时会重发，消费者必须基于 task_id 和业务版本幂等认领。
5. 超过投递期限进入可查询的失败状态或人工重放入口，不能永久静默重试。

建议字段只作设计参考：`id / kind / resource_id / resource_version / payload_version / state / attempts / next_attempt_at / claim_until / last_error`。本次不创建 Model 或迁移。

Outbox 记录“发布成功”不等于业务任务完成，也不等于任意 broker 配置下绝不丢消息。定期对账应扫描已接受但长期未认领的业务任务；在有效期限内重投原 task_id，先核对任务是否已经完成或运行。

### 5.3 Celery 配置与应用语义一起设计

- 区分 Agent 执行、评估、索引和清理队列与 Worker 容量，避免长索引阻塞轻量任务。队列拆分优先服务于隔离，不为每个函数建立新队列。
- 每类任务明确自动重试的异常范围、最大次数、退避和截止时间；参数错误和权限失败不自动重试。
- 评估已经有认领和冻结材料，可作为模式参考；索引需增加版本/阶段检查，不能直接给所有任务添加 blanket autoretry。
- 只有任务具备幂等和崩溃恢复策略后，才考虑 late ACK、Worker 丢失后的重投；它们会引入重复执行，不是无成本的可靠性开关。
- Redis broker 的 visibility timeout 要与最大执行时长和确认策略协同设置，防止任务尚未结束就被再次投递；不能只无限增大超时，否则失联恢复也会变慢。
- 对长任务限制 prefetch，防止一个 Worker 提前占有大量排队任务。软超时用于清理，硬终止不会保证 finally 执行，外部资源仍需补偿。
- 将队列存储与可淘汰业务缓存进行资源隔离。不同 Redis DB 编号不提供内存、故障和淘汰策略隔离。持久化、复制、认证、TLS 与 broker 支持能力需实际验证。

### 5.4 MQ 选择

| 方案 | 适用情况 | 注意点 |
| --- | --- | --- |
| 延续 Celery + Redis | 已有生态、任务规模可控。 | 验证持久化和恢复语义，隔离缓存负载。 |
| Celery + RabbitMQ | 需要更明确的队列路由、确认和消息治理。 | 配置持久消息与队列、发布确认、容量/HA；应用幂等仍不可省略。 |
| Redis Streams | 共享短期事件日志与游标读取。 | 不等于把 Celery broker 替换成 Streams；需要独立设计读者语义。 |
| Kafka / RocketMQ | 存在明确的大规模事件或组织基础设施需求。 | 先验证接入成本和语义，不仅为了简历技术栈更换组件。 |

不使用学习实现的 StudyMQ 承载平台生产任务；它的学习价值与生产消息基础设施选择是不同问题。

## 6. Agent 执行与 API 分离

### 6.1 目标分工

| 角色 | 职责 |
| --- | --- |
| API | 鉴权、校验、创建/恢复/取消请求、查询和 SSE 交付。 |
| 调度与投递 | Outbox、准入、排队期限、幂等分发。 |
| Agent Worker | 认领执行、装配模型/工具、运行图、提交事件和结果、清理资源。 |
| Reconciler | 处理过期租约、未投递任务、孤立资源和数据状态不一致。 |

队列传递 `execution_id + dispatch_generation` 等可验证标识，不传本地 Event、线程句柄或沙箱对象。Worker 根据持久化授权定义与配置版本重新装配，凭据由受控存储解析。

### 6.2 状态模型和会话占用

若选择排队，需要新增明确的调度状态，可使用业务 queued 或独立调度记录，但不能让页面把排队当成已经推理。

当前会话占用唯一约束只覆盖 running、waiting_input。增加 queued 后，要同步处理占用约束、冲突查询、取消、期限、展示和幂等返回，否则一个会话可以同时排入多个本应互斥的任务。

waiting_input 不应长期占用 Worker 或保持一条 Celery 消息未确认。等待状态与表单保存完成后结束执行片段；收到答案时保存 Submission，再为同一个 execution 创建新的调度代际和 outbox。

### 6.3 持久化执行租约

在现有 executor_id 基础上增加或明确 `worker_id / lease_expires_at / generation / heartbeat_at` 等语义：

1. Worker 在短事务中检查状态、代际、期限和取消意图，原子认领执行。
2. 运行期间续租，使用数据库时间或一致的时钟策略。心跳不与长模型请求共用阻塞通道。
3. 事件批次、结果、用量写入校验执行身份和代际；旧 Worker 的迟到写入被拒绝。
4. 租约到期时由 Reconciler 标记待处理，而不是由任意 API 根据本地 Tracker 判断失败。
5. 是否重新执行还需检查检查点、工具副作用和文件依赖；不把租约到期直接等同于安全重跑。

**只保护业务表不足够。** Checkpoint 和 Store 也可能被仍在运行的旧 Worker 写入；需要在框架持久化边界验证代际、提供可靠单写者策略，或在无法确认旧执行退出时禁止自动接管。同理，外部工具调用必须有自己的幂等/查询机制。数据库 fencing 不会自动终止已发出的外部请求。

### 6.4 取消与恢复

取消意图先持久化，消息通知用于加速送达。Worker 定期检查数据库状态和租约，即使取消通知丢失也能最终响应。不要把 cancel 命令放在会被长任务完全占满的执行队列中。

恢复沿用业务任务 ID，使用新执行代际和有效的框架 checkpoint。配置变化沿用当前指纹限制，或未来明确保留版本快照；不能恢复时明确失败原因。工具已执行但结果未知时，优先查询外部结果或要求人工确认，不盲目重放。

业务记录与 Checkpoint 使用不同提交路径时，增加 reconcile 检查：例如框架已中断但业务尚未保存表单、图已完成但回答事务失败。恢复逻辑应能识别这些情况，不能单看某张表的 status。

### 6.5 工具副作用分类

| 类别 | 重试策略建议 |
| --- | --- |
| 只读检索/目录读取 | 有限重试、超时、预算约束。 |
| 支持幂等键的外部写入 | 稳定 operation_id 重试，并保存外部返回标识。 |
| 能查询结果但不支持幂等的写入 | 超时后先对账，确认未生效再决定重试。 |
| 无法确认结果的不可逆操作 | 标记结果未知，停止自动重跑，提供确认流程。 |

可增加工具调用账本记录意图和结果，便于恢复判断；账本不能解决外部系统没有幂等能力的根本限制。当前仅重试只读工具的原则应保留。

## 7. 共享事件通道与 SSE

### 7.1 推荐先统一持久化边界

当前是先实时分发、后批量落库，尾部存在故障丢失窗口。Worker 化的第一版推荐采用“短批次提交数据库 → 发布已提交水位通知 → SSE 读取增量”的方案：

1. Worker 在有效租约下分配 seq，批量写事件并更新已提交水位。
2. 提交后发出 run_id 与 committed_seq 通知，可通过 Redis Pub/Sub 加速。
3. API 根据自身游标查询并交付更高序号的持久事件。多条通知可合并，避免每事件一次查询。
4. Pub/Sub 通知不作为事实来源，丢通知时通过周期补查和重连读取恢复。
5. 业务终态继续与回答、用量和状态同事务保存，提交后才通知。

这个方案使已公开内容来自已提交事件，代价是展示等待一个短批次。批次大小和刷新间隔由首字/延迟目标与数据库压力测量决定。

如果必须保留写库前预览，协议需要区分暂存事件与已提交水位，并定义重连后如何修正未持久化内容；不要用同一个“已收到”标志同时表示展示和可靠保存。

### 7.2 Redis Streams 作为进一步选项

需要共享可回放尾部时可考虑 Streams，但应先明确唯一事实源。如果 DB 为事实源，按提交顺序发布并可从 DB 补齐；不要让 DB 与 Stream 分别生成互不对应的 seq，再依赖猜测去重。

不同 SSE 订阅者都需要看到相同事件，不能直接放入一个竞争消费组，把事件分摊给不同浏览器。可让每个网关独立订阅相关流，或者在网关内部再广播；为每个 Run 建永久消费组也会增加清理负担。

消费者使用 execution_id + seq 去重，按同一 Run 保序；多模型/子 Agent 内容继续按 model_run_id、namespace 和 node 区分。不要追求所有租户事件的全局顺序。

### 7.3 连接与历史治理

- 反向代理关闭 SSE 缓冲，设置匹配长连接的超时与心跳。
- 重新连接重新鉴权，不能因知道 run_id 就读取事件。
- 限制每账号订阅数与慢客户端缓冲；超过阈值让客户端以游标重连。
- 定义事件、快照和最终回答的保留时间。游标早于保留水位时返回明确的快照重置指令，不静默省略历史。
- 大工具输出转存并返回引用时，保留权限、版本与可追溯来源，避免每个事件携带整份文件。

## 8. 工作区、COS 和沙箱资源治理

### 8.1 将失败清理变成可追踪任务

当前 COS 补偿删除和沙箱 dispose 失败主要记录日志。建议持久化 cleanup job，包含精确资源身份、动作、归属、版本、重试时间和结果。

COS 成功更新元数据后，旧 object key 的清理意图可以与数据库变更一起保存。新对象已上传但数据库提交失败时，主事务不能保存清理记录，可使用独立补偿事务；若进程在这之前退出，需要定期按暂存标记、创建时间和引用关系巡检孤立对象。

清理只删除精确 object key，不能使用可变化的业务路径。检查引用并建立删除/失效状态，避免检查结束后对象又被发布引用；上传对象使用唯一 key，未完成对象应处于不可交付状态。设置宽限期，避免巡检把正在上传但尚未提交的对象删掉。

### 8.2 多 Worker 下的沙箱所有权

第一阶段可以保留 Worker 本地池，但要增加远程实例的持久化归属清单及 Reaper：记录 provider_instance_id、会话、worker、租约代际、到期时间和清理状态。远程实例创建后尽快登记，同时使用可追踪标签或创建请求 ID，处理“已创建但还未登记就崩溃”的窗口。

队列消息过期不能直接作为删除依据。删除前通过 CAS 将资源从可租用改为 deleting，并检查无人占用、代际未变化；新的租约获取必须拒绝 deleting 状态，避免检查后又复用的竞态。使用实例 ID，不按可能复用的会话名称盲删。

Provider 的自动停止/删除作为最后兜底，平台仍应观测清理失败和孤立资源费用。重用 Daytona 只清理指定目录，不保证整个环境完全重建；对需要更强隔离的业务采用一次性实例或受控镜像策略。

### 8.3 保留显式交付语义

deliver_file 成功返回应继续表示正文及元数据已经保存。若改为异步上传，必须新增 pending/ready 状态及对应用户交互，不能任务刚入队就返回“已保存”。

临时工作副本默认不恢复。确需自动接管文件任务时，应在受控执行边界保存必要的输入和中间产物清单，记录对象版本；不默认把全部脚本、缓存和未授权文件同步到 COS。

Skill 继续按授权装配、压缩上传和安全解包。若增加跨轮缓存，缓存键必须覆盖包内容哈希、授权集合和运行环境版本，避免授权撤销后继续暴露旧 Skill。

## 9. 文档索引、知识库和评估任务

### 文档索引

现有文档链路已经使用 Celery，应重点完善可重复执行与跨库收敛：

1. 用 document_id、source_version、embedding_fingerprint 和 index_generation 标识一次索引构建。
2. 分段和向量写入使用稳定或版本化标识，重复消息不产生不可控重复记录。
3. 每批检查资源未被删除且版本仍有效，旧任务不能覆盖新索引或让已删除文档重新可见。
4. 新索引构建完成后再切换可见版本，旧版本后台删除；查询时保留账号和可用状态过滤。
5. 对 SQL、关键词索引和 Weaviate 做可观测对账；无共享事务时依靠阶段状态、幂等写入和补偿，不能宣称跨库原子提交。

大批文档分批调度，限定文件大小、解析时间、分段数和 Embedding 并发。不要让一个包含大量 document_ids 的任务一直占用 Worker，失败重跑也应尽量定位到文档或批次。

### Agent 评估

保留已有冻结材料、原子认领、截止时间和结果保护。增加可靠投递、积压告警与失败分类；重试时固定 task_id 和评估版本。模型超时后重新评分会产生额外成本，不能和结果查询重试混为一谈。

评估结果 completed 继续表示报告生成，不等于 accepted。平台发布前可准备小型代表性验收集，比较核心任务的完成、规则通过与弃评情况；隔离文本评估不能代替真实工具、权限与外部副作用的集成验证。

## 10. 配置、数据与发布恢复

### 10.1 多种数据源的权威边界

| 数据 | 权威来源建议 | 恢复关注点 |
| --- | --- | --- |
| 业务任务、提交、回答和事件 | PostgreSQL 业务表。 | 同事务终态、幂等键、保留水位。 |
| 图执行状态 | Checkpointer。 | 框架版本、图定义版本、单写者与业务状态对账。 |
| 长期记忆、历史归档 | Store。 | 作用域、容量、备份及与应用删除的关联。 |
| 文件正文 | COS，与 SQL 元数据引用关联。 | 对象版本、备份保留、孤立/悬空引用。 |
| 向量索引 | Weaviate 的已发布索引版本。 | 原文、分段规则与模型指纹是否足以重建。 |
| MQ 消息与通知 | 调度或加速通道。 | 业务任务可对账；不作为唯一结果数据库。 |

### 10.2 配置与运行时版本

为运行记录明确 runtime/protocol/definition 版本。现有配置指纹保护恢复不混用定义，但还需要考虑升级 DeepAgents、LangGraph 或工具 Schema 后旧 Checkpoint 是否兼容。

不兼容版本可以排空旧任务、保留旧 Worker 处理旧版本或明确结束旧任务；不能对不兼容快照盲目启动新代码。权限在真正执行前复核，保留配置快照不意味着永久保留已撤销的授权；凭据通过引用解析，不把密钥固化进队列。

### 10.3 数据恢复与迁移

建立 PostgreSQL 备份及时间点恢复策略，记录 Checkpointer/Store 是否与业务库使用同一实例或独立库，实际演练恢复后能否读取问答、表单、记忆和文件。COS 删除保护、版本保留及加密密钥恢复也要纳入演练；单纯恢复 SQL 无法找回已删除正文。

定义数据保留策略：事件、Checkpoint、归档、记忆与用户文件分别处理。删除应用/账号涉及多个存储，应留下可追踪的删除任务；备份中的数据如何到期由业务保留要求决定。

新增字段采用兼容旧读写的迁移，索引构建和回填评估锁与时长。遵循仓库约定，本方案不生成或执行数据库迁移。

## 11. 模型、工具、配额与访问边界

### 预算与超时

- 当前主图有模型/工具调用限制，但同步子图不自动共享全部平台中间件，恢复还会重新装配。增加 run 级、主子 Agent 合计的持久化预算。
- 预算至少覆盖调用次数、输出限制、累计时间、并发和可获得的 Token/成本。缺失供应商用量时记录 unknown，不能当作零成本。
- 准入阶段按账号/应用和 Provider 配额限制请求，执行阶段持续扣减或保留预算，结束后按实际用量结算。并发任务之间需要原子额度操作。
- HTTP、排队、模型、工具、沙箱和业务 Run deadline 分层设置，重试消耗同一剩余预算；取消与硬超时不撤销外部副作用。
- 对供应商 429/暂时故障使用有界退避和抖动，结合熔断/并发控制，避免 Worker 增加后同时重试放大压力。不要无提示切换到不兼容或未授权模型。

### 已有权限基础上的生产验证

平台已有入口鉴权、资源归属与沙箱隔离，应验证 WebApp/API/内部协议在多实例下仍复用同一可信身份和授权规则。文件 URL、事件订阅、后台任务与工具执行都要在服务端检查作用域。

针对 MCP、HTTP 工具和网页读取，核对目标地址与网络出口策略，防止访问不应暴露的内网服务；鉴权材料不进入普通日志、模型可见正文和队列载荷。工具返回、检索文档和 Skill 内容不能自行提升工具权限。

Shell 运行需要 CPU、内存、进程数、磁盘与网络边界；当前 Bubblewrap 的 namespace、超时和输出限制不自动等于完整资源配额。保留 local_shell 的开发环境限制，多租户生产验证只读挂载和跨作用域不可访问。

Redis 限流目前存在故障时放行路径。对便宜只读接口和高成本模型/执行入口分别定义降级策略；可采用保守本地额度或拒绝高成本新任务，同时保留状态查询与取消能力。不要把“Redis 不可用一律放行”当成默认生产策略。

## 12. 可观测性与部署运维

### 指标与关联

| 类型 | 推荐观测 |
| --- | --- |
| 任务 | 接受/拒绝数、排队时长、活跃数、等待输入数、取消完成时间、租约超时。 |
| 投递 | Outbox 最老待发年龄、失败次数、重复认领数、已接受未运行数。 |
| 模型/工具 | 延迟、429/超时、重试次数、调用预算、实际与未知用量。 |
| 流式 | 首字交付、事件提交滞后、背压、SSE 断开/重连、快照恢复耗时。 |
| 存储 | 业务/Checkpoint/Store 各连接池、锁等待、事件增长、COS 孤立引用。 |
| 资源 | 沙箱创建/复用/失败、活跃/空闲数量、清理积压和费用。 |
| 索引/评估 | 排队、处理阶段失败、旧版本任务丢弃、规则通过和弃评。 |

保留当前 run_id、executor_id、app_id 等关联日志。需要跨服务追踪时再增加 OpenTelemetry 等实现，记录调用结构与耗时，默认不收集完整提示词、文件和凭据。run_id 等高基数字段放日志/Trace，不作为所有时序指标的标签。

告警优先关注用户影响：已接受任务长时间无进度、投递停止、清理持续失败、事件写入失败、依赖连接耗尽。阈值由目标与基线确定，不把固定数字当作普适标准。

### 部署行为

- liveness 只判断进程是否需要重启；readiness 判断能否接收当前类别新请求。不要因外部模型短暂失败就重启全部服务。
- 发布时先停止接收新任务，排空或受控终止现有执行；Worker 超出宽限期后由租约和 Reconciler 收敛，不能依赖退出钩子必定运行。
- API、Agent Worker、索引/评估 Worker 设置独立容量与连接池预算，避免进程数乘以每池连接数后超过数据库限制。
- 固定 Python、依赖、框架和沙箱镜像版本，记录部署版本；模型别名变化也应进入问题定位信息。
- 多实例前核对所有进程内状态：Tracker、EventHub、取消信号、沙箱池、缓存、线程锁和本地路径，逐个明确是否可本地化或必须共享。

## 13. 分阶段实施与回退

| 阶段 | 工作包 | 验收门槛 | 回退原则 |
| --- | --- | --- | --- |
| A：受控单实例 | 保持单 Worker、有界执行；补监控、超时、备份恢复、SSE 代理与容量基线。 | 满载可拒绝，重启结果可解释，备份可恢复。 | 保持现有任务语义，不承诺自动接管。 |
| B：可靠异步任务 | Outbox、消费幂等、清理任务、索引版本与对账。 | 重复投递不重复生效，发送失败可追踪恢复，清理不误删。 | 已接受 outbox 仍需处理，不通过删队列回退。 |
| C：共享交付基础 | 提交水位通知、共享 SSE 读路径、持久取消与执行代际校验。 | 任一 API 可恢复同一运行，通知丢失能补齐。 | 保留 DB 历史和旧客户端协议兼容。 |
| D：独立执行 Worker | 新调度状态、租约/续租、受控接管、资源归属、主子总预算。 | 双 Worker 竞争只有合法写者，失联可收敛，外部未知结果不盲重放。 | 新旧执行器按任务版本分流，不能同时认领同一任务。 |
| E：规模化优化 | 分租户公平性、必要的事件存储优化、成本调度与容量扩展。 | 在代表性负载下满足约定目标。 | 按流量和任务版本逐步撤回，保留数据兼容。 |

每阶段先按内部应用或小范围流量灰度。数据库、Checkpoint 和协议版本兼容比“能回滚容器镜像”更重要。阶段 C/D 的中间形态必须禁止仍基于本地 Tracker 的孤儿收敛误处理远端任务。

## 14. 故障与容量验收清单

以下为计划验证的场景，并非已执行结果。

| 场景 | 期望行为 |
| --- | --- |
| 业务事务提交后、投递前杀进程 | Outbox 后续投递，或过期状态明确可查。 |
| broker 接受消息但 Relay 未更新状态 | 允许重发，消费者按原 task_id 不重复产生业务效果。 |
| 两个 Worker 收到同一执行消息 | 只有一个合法代际可运行/写入，其余退出。 |
| Worker 失联但旧模型请求稍后返回 | 旧业务写入被拒绝；Checkpoint/Store 与外部动作也有明确处置。 |
| 用户回答表单与取消同时到达 | 按事务顺序得到唯一可解释状态，无重复恢复。 |
| SSE 通知丢失、网关切换、慢订阅 | 根据已提交游标补齐；过期游标明确重置快照。 |
| 最终结果已提交，通知前进程退出 | 查询和重连仍返回已完成结果。 |
| COS 上传成功但元数据失败 | 保留失败结果，补偿或巡检清理孤立对象，不误删正在提交对象。 |
| 清理消息延迟至沙箱已重新租出 | 代际/CAS 校验阻止旧清理删除新租约资源。 |
| 旧索引任务晚于文档更新/删除完成 | 旧 generation 不发布，不复活已删除资料。 |
| Redis 故障 | 队列与限流按策略降级，高成本入口有容量保护，取消/查询尽量保留。 |
| 框架版本升级后恢复旧表单 | 兼容版本继续，否则明确拒绝，不静默损坏状态。 |
| 达到租户预算或供应商配额 | 新调用受控拒绝/等待，重试不绕过预算。 |
| 从备份恢复完整环境 | 能核对业务记录、Checkpoint、记忆、文件引用及索引版本。 |

容量测试分别测并发运行数、长连接数、事件速率、大工具输出、文件大小和索引负载，记录硬件、模型、配置与样本。先用可控模拟服务验证平台瓶颈，再用真实模型验证端到端延迟，不用供应商响应波动掩盖平台问题。

## 15. 保留哪些现有设计

- 会话占用、表单校验、提交幂等和执行身份校验继续保留，MQ 不替代业务一致性。
- deliver_file 成功语义和文件版本控制继续保留，不能为异步化牺牲结果真实性。
- 框架事件规范化和平台 seq 继续保留，不能把消息代理 ID 直接冒充业务序号。
- 只读工具有限重试、授权装配、上下文动静分离和按需记忆继续保留。
- 主模型一次次工具循环由框架管理，不把每个模型调用或文本分片拆成独立 Celery 任务。
- 长期记忆和文件更新仍需事务/版本控制；事件广播只通知变化，不替代真实读取。

## 16. 面试中的架构演进回答

> 当前文档处理和评估使用 Celery，交互式 Agent 在单 API 进程的有界线程池中运行，已经有状态、幂等和事件恢复机制。生产化我会先补可靠投递、清理补偿、预算与恢复验证；有独立扩容需求后再把执行迁移到 Worker。同时改造执行租约、Checkpoint 写入边界、跨进程取消和共享事件交付，而不是单独把执行函数包成队列任务。MQ 提供调度和通知，数据库仍保存业务事实，外部副作用仍需要幂等或对账。

这段描述的是改造思路，不能写成已经完成的多实例生产实践。
