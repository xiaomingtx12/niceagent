# 简历编写思路

## 1. 项目介绍先讲业务，再讲迭代

项目介绍回答三个问题：用户可以完成什么任务，怎样配置和使用平台，系统经历了什么演进。

推荐组织为：知识问答、资料分析、内容生成及文件处理 → 在线配置模型和能力、WebApp/API 交付 → 从基础对话和工具调用迭代至多 Agent、工作流及评估，从自建 LangGraph Agent 演进为 DeepAgents 运行时。

介绍中的「迭代」应说明新增能力或职责变化。避免只写「持续优化架构、提升智能化水平」，也不把切换框架直接当成已测量的性能收益。

## 2. 每条的基本结构

**模块职责：实现了什么；关键机制如何解决具体问题。**

正文通常约 70～90 字，标题保持可扫描；个别英文标识会增加字符数，不必为了机械凑字数删掉关键边界。保留一条主线、两到三个有解释价值的机制，其余细节进入面试材料。

以任务恢复为例：

- 能力：任务等待用户信息时暂停，回答后继续。
- 框架机制：ask_user、interrupt、Checkpoint、Command(resume)。
- 平台实现：表单校验、提交记录、执行权认领、取消状态协调。
- 结果：同一任务能正确恢复，网络重试不会重复触发执行。

只写「基于 Checkpoint 实现恢复」会掩盖交互和业务控制；把全部方法名写进去又会失去可读性。简历保留机制组，面试展开方法和事务边界。

## 3. 八条各自怎样写

| 条目 | 叙述顺序 | 重点难点 | 留到面试展开 |
| --- | --- | --- | --- |
| Agent 架构演进与在线装配 | 重构起点与终点 → 配置范围 → 授权和执行约束。 | 业务服务与框架运行时分工、子 Agent 能力边界。 | MCP 缓存、工具重名、只读重试、模型连接复用。 |
| 任务管理与交互恢复 | 统一入口 → 暂停恢复 → 幂等与并发。 | 图状态、业务状态与执行权共同约束恢复。 | 输入批次、配置指纹、锁顺序、孤儿任务处理。 |
| 流式事件与断线续传 | 规范化 → 实时分发和存储 → 历史衔接 → 终态。 | 两种交付速度、持久化水位和客户端游标。 | 有界队列、慢消费者、事件身份、进程崩溃边界。 |
| 上下文工程与长期记忆 | 动静装配 → 容量控制 → 跨会话存取。 | 稳定前缀、输入只注入一次、按需记忆。 | 模型预算、压缩与归档差异、内容摘要校验。 |
| 沙箱执行与文件交付 | 路由 → 创建复用回收 → Skill 部署 → 产物。 | 资源所有权、独占租约与临时/持久化边界。 | TTL、代际保护、压缩阈值、COS 补偿清理。 |
| 在线知识库与混合检索 | 文档管理 → 索引 → 召回融合 → Agent 接入。 | 关系数据与向量索引的对应、模型指纹一致性。 | 分段规则、关键词算法、缓存与检索效果衡量。 |
| 可视化工作流引擎 | 配置转图 → 变量和依赖 → 调试发布 → 工具化。 | 条件汇聚与并行 fan-in 的区别。 | Pydantic 校验、状态 reducer、动态参数 Schema。 |
| Agent 评估与执行验收 | 评估范围 → 裁判和规则 → 修订 → 证据一致性。 | 冻结输入、候选版本与程序证据绑定。 | Celery 认领、弃评、超时、评分轮数和覆盖检查。 |

## 4. 为什么这样拆分

任务管理决定任务是否能继续，事件链路决定客户端如何接着看。两者分别成条，能够展示服务控制和实时通信两类能力。

上下文管理控制信息如何进入模型，知识库提供外部资料检索。文件记忆与 RAG 的访问方式、作用域和数据生命周期不同，不应混成「记忆检索优化」。

工作区和沙箱属于同一条文件执行链路：本地准备、远程运行、显式交付、资源回收。Skill 的在线选择放在装配模块，压缩上传和只读部署放在沙箱模块，分别解释配置和落地。

工作流适合表达确定的节点和依赖；Agent 通过模型动态决定调用。工作流最终可以封装成 Agent 工具，体现两种执行方式的组合。

评估独立成条，强调输出质量与验证边界，避免只在运行时后面附一句「支持评测」。

## 5. 框架能力与个人实现怎样措辞

| 内容 | 适合的表述 | 不应扩大为 |
| --- | --- | --- |
| DeepAgents 的规划、SubAgent、摘要、Rubric | 基于、接入、适配、配置。 | 自研全套 Agent 调度与自动修订算法。 |
| LangGraph 的 interrupt、Checkpoint、图执行 | 结合、封装、使用。 | 单靠 Checkpoint 保存所有系统状态。 |
| 平台身份、装配、幂等、事件和资源生命周期 | 设计并实现具体机制。 | 未核实的全团队独立负责、企业规模生产落地。 |
| 稳定提示词前缀、批量落库、懒加载 | 说明减少变化、写入次数或无效启动。 | 没有测量的命中率、延迟和成本改善百分比。 |

## 6. 写作修正示例

| 原句 | 问题 | 更准确的写法 |
| --- | --- | --- |
| 基于 Checkpoint 实现人机交互。 | 省略工具、表单和业务恢复。 | 结合 ask_user、图中断与 Checkpoint，并以校验和幂等控制恢复。 |
| COS 防止并发覆盖。 | COS 存正文，平台校验版本。 | 显式保存产物至 COS，以平台版本校验防止旧副本覆盖。 |
| Sandbox 每轮执行完销毁。 | Daytona 可归还会话池。 | 会话独占复用，按 TTL、容量和失效状态回收。 |
| 上下文动静分离提升缓存命中率。 | 缺少实际测量。 | 稳定固定前缀，避免本轮参数和重复规则改写前缀。 |
| 关键词检索采用 BM25。 | 当前使用 Jieba 与关键词命中计数。 | 关键词召回与向量检索融合。 |
| 评估实现自动学习。 | 修订发生在推理阶段，不更新参数。 | 基于裁判反馈进行有限轮次修订与验收。 |

## 7. 篇幅与岗位适配

Agent 后端岗位优先：架构演进、任务恢复、上下文、沙箱，然后按篇幅加入流式、RAG、工作流和评估。通用后端岗位可以把任务一致性、事件与资源生命周期前置。RAG 岗位可以把知识库前置，但仍需要如实解释检索算法。

这些材料是 8 条候选主线，正式简历可选 5～8 条。减少条目时按岗位取舍，不把两个完整模块压成难以阅读的超长句。

## 8. 提交简历前的准备

每条至少能回答：业务场景是什么、一次调用怎样经过代码、为什么用这些机制、异常或并发时怎么处理、哪些来自框架、现在的边界是什么。个人贡献、真实问题和实测指标另行填入，不把模拟案例当作真实线上事故。
