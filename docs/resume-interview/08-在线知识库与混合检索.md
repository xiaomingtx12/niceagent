# 在线知识库与混合检索：面试准备

## 简历主张与编写思路

这条沿文档变成可用知识的链路展开：在线管理、解析清洗分段、向量和关键词索引、检索融合、Agent/工作流接入。重点是完整工程链路与检索边界，不把组件接入写成自研检索算法。

## 一分钟口述

平台提供知识库、文档和分段管理，后端处理文档解析、清洗、切分及索引，关系库存权限、状态和分段元数据，Weaviate 提供向量检索。查询先校验账号可访问的知识库，并检查所选库是否使用相同向量模型指纹。检索支持语义、关键词和混合模式；关键词侧通过 Jieba 提取查询词，再按分段命中计数排序，混合模式使用 EnsembleRetriever 融合两路结果。最终将片段组织成工具返回，并记录查询和命中，供 Agent 或工作流使用。

## 文档到检索的链路

1. 创建知识库并绑定向量模型配置，上传并登记文档。
2. 文档处理任务进入解析、清洗、切分、索引和完成等处理阶段。
3. 根据规则切分文本，保存 Segment 和关联标识，建立向量及关键词索引。
4. 查询时解析账号、知识库 ID、检索策略、Top K 和语义分数阈值。
5. RetrievalService 筛选账号所属知识库，取得对应向量模型绑定，检查指纹一致性。
6. 调用语义或关键词检索器，混合模式使用两路结果融合并取前 K。
7. 返回片段内容与元数据，更新查询记录和命中信息；工具适配后接入 Agent 与工作流。

关系库和向量库不是一个事务系统。分段状态、索引更新与异常处理应按实际任务链路解释，不能直接宣称跨库强一致或自动回滚所有外部写入。

## 三种检索方式

| 方式 | 当前实现 | 适合的问题 |
| --- | --- | --- |
| 语义检索 | SemanticRetriever + Weaviate，接收 k 与 score_threshold。 | 查询措辞和原文不同但语义相关。 |
| 关键词检索 | Jieba 提取查询关键词，从 KeywordTable 匹配分段，Counter 按命中次数排序。 | 明确名词、术语和关键词匹配。 |
| 混合检索 | EnsembleRetriever，当前两路权重各 0.5，融合后取前 K。 | 结合两路召回的互补性。 |

当前关键词实现不是 BM25，也不是 Elasticsearch。混合融合不等于额外调用交叉编码器 reranker；权重 0.5/0.5 是当前配置，不应说经过离线评测达到最优。

## 为什么要校验向量模型一致性

即使向量维度相同，不同 Embedding 模型生成的空间也不能直接比较。当前一次跨库检索要求所选知识库绑定相同模型指纹，用它确定查询 Embedding 和索引来源。模型升级需要考虑重建索引和迁移，不能只替换查询模型配置。

## 权限在哪里生效

知识库归属首先在 Service 侧根据账号与 dataset_ids 过滤，检索器收到已授权范围。向量检索还携带相应范围和可用性条件。不要把模型提示词里一句「不要读取其他用户资料」当成权限控制。

当前代码会筛选请求中可访问的知识库并拒绝没有可用库的情况，不能说任意混入一个未授权 ID 就一定整批拒绝。关键词路径的可用状态与关键词索引维护有关，面试时不要泛称两个检索器所有过滤实现完全相同。

## 典型追问与回答要点

**为什么切分文档？**

控制检索粒度和模型输入体积。块过大可能稀释关键内容，过小会丢失语义上下文；规则应结合文档结构与查询类型选择，没有一组大小适合所有资料。

**为什么不只用向量检索？**

专有名词、数字编号等可能更适合关键词匹配；关键词又容易漏掉同义表达。混合用于互补，但是否改善效果需要查询集验证，不能根据架构直接推断准确率。

**检索不准怎么排查？**

先检查文档是否解析完整、分段是否合理和索引是否完成，再检查绑定模型、检索范围、Top K/阈值及两路结果。最后再考虑权重、重排序或查询改写，不先把所有问题归咎于生成模型。

**怎样衡量效果？**

准备带相关片段标注的查询集，比较向量、关键词、混合的 Recall@K、MRR 和延迟；回答质量另行检查事实和引用。当前材料不包含已跑出的指标，这属于建议采集方案。

**怎样降低重复 Embedding 开销？**

项目有 Redis 支持的 CacheBackedEmbeddings；应结合模型绑定和缓存键区分来源。缓存减少重复计算，不会自动修复更换模型后的旧索引。

## 场景推演

用户查询某产品型号的安装限制。先看关键词路是否命中型号，再看语义路是否召回「安装条件」的同义段落。若文档解析阶段把表格列错位，增加 Top K 不能根治，需要先修复输入材料和分段质量。
