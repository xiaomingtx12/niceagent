# 流式事件与断线续传：面试准备

## 简历主张与编写思路

顺序是「统一事件 → 实时交付与批量存储 → 历史和增量衔接 → 结果提交后终态」。核心问题是用户怎样及时看到长任务进度，刷新后怎样恢复，以及完成状态什么时候可信。

## 一分钟口述

我把框架事件先转成稳定的 AgentEvent，再投影为平台协议事件，补齐业务身份和连续序号。事件先进入有界待写队列并实时分发，独立写线程按数量或时间批量落库。客户端重连先获得固定已提交水位的历史快照，再订阅更高序号的事件；内存尾部覆盖不到时回数据库补齐。执行结束会先排空事件写队列，再在事务内提交回答、状态和终态事件，提交后才公开业务完成。当前实时尾部在进程内，因此部署使用单 API Worker。

## 一条事件如何到达客户端

1. AgentExecutor 消费框架 stream_events；Normalizer 保留消息边界、分支、节点和模型调用身份，转换为 JSON 兼容载荷。
2. EventProjector 过滤不公开内容、绑定本轮回答 ID，为公开事件和业务主动事件分配平台 seq。
3. EventBuffer.emit 在同一锁内登记待写事件并发布到实时 EventHub，唤醒 SSE 订阅者。
4. 后台写线程按批次或超时落库，数据库提交在队列锁外执行。提交成功才移除队列前缀和推进已保存水位。
5. SSE 正常读取内存尾部；有缺口或无活动 EventHub 时查询数据库，等待新事件期间释放数据库连接。

## 四个容易混淆的标识

| 标识 | 范围与用途 |
| --- | --- |
| Core sequence | 本次执行片段内递增；恢复片段会重新开始，不能当业务续传游标。 |
| 协议 seq | 一个业务执行内的连续事件序号，用于持久化、重连和客户端去重。 |
| model_run_id + namespace + node | 区分主子 Agent 或并行模型调用，防止内容块串线。 |
| 已提交水位 | 数据库已经确认保存的事件边界；实时展示可能比它更靠后。 |

数据库事件写入以 execution_id 与 sequence 约束重复，订阅过滤不会阻断扫描游标前进。

## 快照怎样和实时事件衔接

假设查询时数据库已提交到 100，内存中还有 101～106：

1. 固定水位 100，只合并不超过它的已保存内容块，生成恢复快照。
2. 客户端应用快照，后续游标从 100 开始。
3. SSE 交付 101 之后的内存事件；更晚的新事件继续按相同序号追加。
4. 若内存尾部已淘汰所需前缀，先从数据库补齐，再接回实时尾部。

快照是给页面恢复展示的材料，不是 LangGraph Checkpoint。重连不重跑 Agent，图恢复也不依赖重新播放 SSE 给模型。

## 为什么不能每个分片同步落库

分片频繁时，每条事务会增加数据库往返并让展示等待存储。当前将交付和批量写入分开，减少事务次数；队列有上限，存储落后时生产者会等待，防止内存无限增长。批量线程失败会唤醒生产者并保留待处理数据，收尾再尝试处理尾批，不能继续假装成功。

这个取舍意味着实时展示不是同步持久化承诺。若进程在批量提交前突然退出，用户已看到但尚未落库的尾部可能丢失；不能写成任意故障下事件绝不丢失。

## 为什么最后再发布终态

框架结束只说明图不再执行，不说明业务回答和快照已保存。平台先 drain_and_close，再原子保存回答、用量、状态和终态事件，提交后发布。这样用户看到业务 completed 时，可以读取已保存结果。waiting_input 也要在表单状态保存后通知客户端。

## 典型追问与回答要点

**为什么用 SSE？**

主要是服务端持续向客户端发送执行过程；命令、取消和表单提交走独立 HTTP 请求。单向事件传输适配这个交互模式。没有用它替代业务控制接口。

**慢客户端会拖住所有任务吗？**

订阅从各自游标读取实时尾部，超出尾部范围从库补齐；生产端另外受待写队列背压影响。需要区分客户端慢与数据库写入慢。

**重连会重复收到事件吗？**

客户端应按 run_id 和 seq 识别已应用事件，服务端按游标发送后续事件。快照与增量共享边界，但网络重连不能声称提供全链路 exactly-once 传输。

**为什么单 Worker？如何扩展？**

当前运行登记、取消信号和实时尾部都在进程内。多 Worker 需要共享事件设施、执行所有权和跨进程取消路由等设计。Redis Stream 或消息总线属于可选后续方案，本项目并未把它们用于这条实时链路。

**开启输出审核后还逐字公开吗？**

Core 的审核交付可能缓存整轮事件，通过审核后才公开；因此实时展示还受审核策略影响，不能承诺所有配置都有相同首字体验。

## 面试前准备

演示输出中刷新、工具执行中重连、并行子 Agent 内容区分以及结果完成后刷新。观察首字时间、每批事件数和重连恢复耗时；不要只展示最终聊天文本。
