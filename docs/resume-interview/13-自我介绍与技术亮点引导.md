## 6. 技术难点展开：场景—问题—机制—边界

每段约 1～2 分钟。先讲具体例子，再解释对象、状态和事务；最后说清实际保证与边界。下面的例子用于解释机制，不包装成发生过的生产事故。

### 6.1 任务交互恢复

> 比较典型的场景是，Agent 执行到一半发现缺少必要信息，需要向用户提问。这里不只是保存一个 Checkpoint，还涉及业务任务状态、待填表单和恢复请求。
>
> 我把一轮业务任务和后台执行片段分开：用户补充答案后仍然是同一个任务，但恢复会分配新的执行标识。ask_user 通过图中断提出表单，Checkpoint 保存图状态，平台保存 waiting_input 和待填信息。提交时先校验表单和批次，相同答案重复提交返回原回执；答案保存和新执行权认领在同一事务完成，再启动恢复。
>
> 结果写入时检查 executor_id，防止旧执行的迟到结果覆盖当前状态。取消也需要协调：等待输入时可以直接取消；已经恢复执行时记录取消请求并通知执行器。这保证的是状态和写入资格正确，不意味着能立即中断所有外部模型调用。

追问准备：

- **为什么用行锁？** 将同会话的检查与创建、状态更新串行化；不在整个推理期间持锁。
- **业务任务和执行片段有什么区别？** run_id 保持稳定，executor_id 随恢复片段变化。
- **Checkpoint 为何不够？** 不负责业务权限、提交幂等、表单记录和临时文件管理。
- **取消与恢复同时发生？** 在受锁保护的状态更新顺序下，分别进入待填取消或运行中停止流程。

深入材料：[任务管理与交互恢复](04-任务管理与交互恢复.md)。

### 6.2 工作区、沙箱与文件交付

> 文件任务未必需要执行脚本，所以每轮先创建本地临时工作区，通过 CompositeBackend 路由工作区、Skills 和记忆。普通文件操作可以在本地完成，首次 execute 等需要远程环境的操作才触发沙箱初始化。
>
> Daytona 用凭据作用域和会话身份申请独占租约。池里有未过期空闲实例就复用，否则创建；同一会话正在占用时拒绝再次使用。复用后重新准备工作目录和本轮授权 Skill，Skill 根据压缩收益选择打包上传，并做路径校验和只读保护。
>
> 产物通过 deliver_file 显式保存，COS 保存正文，数据库记录版本，防止另一会话的旧副本覆盖新内容。执行退出后统一释放资源，可复用实例归还池，按 TTL、容量和失效条件回收。Checkpoint 不保存临时目录，资源回收也不自动上传所有文件。

追问准备：

- **什么时候不启动沙箱？** 普通问答、读取 Skill 说明，以及远程启动前的工作区文件操作。
- **复用按什么范围？** 凭据加账号、应用、会话和 Agent 身份；Daytona 池位于进程内。
- **为什么还有文件并发？** 持久化文件跨会话共享，沙箱互斥不等于文件库互斥。
- **异常如何清理？** 初始化失败释放；执行器 finally 关闭资源，清理去重并汇总错误；异常进程退出仍需 Provider 兜底。

深入材料：[工作区沙箱与文件交付](07-工作区沙箱与文件交付.md)。

### 6.3 流式事件与断线续传

> 用户刷新页面时，任务可能还在执行，所以我把执行过程保存成统一事件，并为平台事件分配连续序号。实时分发走 SSE，持久化由后台线程批量完成，避免每个文本分片都同步提交事务；待写队列有上限，数据库落后时通过背压限制内存。
>
> 重连先固定已提交水位，比如 100，合并不超过 100 的历史快照，再接收更高序号的增量事件。如果内存尾部已经覆盖不到游标，就从数据库补齐。任务收尾先排空待写事件，再提交回答、状态和终态事件，提交后才发布业务完成。
>
> 当前实时缓冲和执行控制在 API 进程内，所以使用单 Worker。实时显示可能领先数据库，进程突然退出时不能保证尚未提交的尾部不丢失；这和提交后发布终态是两个不同保证。

追问准备：

- **为什么用 SSE？** 执行过程主要单向推送，命令和表单走独立 HTTP。
- **SSE 重连会重跑模型吗？** 不会，只恢复展示；图恢复是另一条控制链路。
- **批量落库失败怎么办？** 保留失败批并通知生产端错误，收尾处理尾批，不能直接宣布成功。
- **如何多 Worker？** 需要共享事件、执行归属和跨进程取消等设计，属于后续扩展。

深入材料：[流式事件与断线续传](05-流式事件与断线续传.md)。

### 6.4 上下文工程

> 我把固定规则、应用定义和本轮输入分开装配。固定规则保持前缀稳定，应用配置随后加入，本轮规划选项只随新 HumanMessage 注入一次，恢复只传答案；Skill 元数据稳定排序，避免重复追加说明。
>
> 上下文增长后，根据模型窗口和输出预留配置预算，复用 DeepAgents 的摘要压缩，并归档历史和大工具结果。长期记忆按账号与应用保存在 Store 文件中，由 Agent 按需读取，不每轮全量注入。稳定前缀为缓存复用创造条件，但具体缓存收益要测量；摘要也不保证所有历史细节无损保留。

深入材料：[上下文工程与长期记忆](06-上下文工程与长期记忆.md)。

## 7. 必须准备的架构追问

### 为什么从 LangGraph 重构到 DeepAgents？

> 随着加入文件操作、Skills、子 Agent 和上下文压缩，Agent 层需要共同管理这些能力。我选择复用 DeepAgents 的能力与扩展点，将平台工作集中在配置授权、运行装配、任务状态、事件协议及资源生命周期上。DeepAgents 底层仍使用 LangGraph，工作流也继续用 LangGraph，因此这次改变的是 Agent 层的组织方式，而不是彻底移除 LangGraph。

然后选择一个真实改动展开，例如子 Agent 显式授权、平台中间件顺序或 Backend 路由。没有迁移前后的测量，不报告耗时或代码量改善数字。

### 既然用了框架，你具体做了什么？

| 框架提供 | 平台实现或适配 |
| --- | --- |
| 子 Agent、规划、文件工具、摘要。 | 在线配置解析、主子 Agent 授权、运行资源与路径路由。 |
| interrupt、Checkpoint、Command。 | 表单批次、幂等提交、业务状态和执行权控制。 |
| 原生执行事件。 | 协议规范化、业务序号、批量存储与重连续传。 |
