# 可视化工作流引擎：面试准备

## 简历主张与编写思路

核心问题是「画布配置怎样变成可运行程序」。介绍配置转换，再展开变量、条件与并行依赖，最后交代调试发布和 Agent 工具化。前端拖拽本身不是这条后端描述的重点。

## 一分钟口述

后端接收画布节点与连线，先校验节点类型、唯一标识、边引用以及变量等配置，再根据节点类型创建执行对象并编译为 LangGraph StateGraph。普通边表示依赖，意图分类结果驱动条件路由；多个并行来源汇聚时要等待全部来源，互斥条件分支汇聚则不能等待没被执行的分支。工作流保留草稿和发布配置，支持流式返回节点结果。它本身继承 BaseTool，参数 Schema 从开始节点动态构建，因此可以被 Agent 作为工具调用。

## 从画布到执行图

1. WorkflowService 读取草稿，校验图配置及引用的模型、工具、知识库等资源。
2. WorkflowConfig 将 JSON 转成节点/边数据对象，校验类型、唯一性和引用关系。
3. Workflow._build_workflow 创建 StateGraph(WorkflowState)，按 NodeType 映射成执行节点。
4. 生成节点标识并建立普通边、条件边，配置开始与结束节点。
5. 根据来源类型选择独立边或 fan-in 边，compile 得到可执行图。
6. 调试通过 stream 返回节点状态与结果；发布前再次校验并保存发布图。
7. Agent 调用时由 BaseTool 参数解析输入，执行图并返回 outputs。

## 支持哪些节点

当前映射包括开始、结束、LLM、模板转换、知识库检索、代码、工具、HTTP 请求和意图分类。描述已有类型即可，不把 Agent 沙箱 Provider 的实现直接套到工作流代码节点，两者需沿各自代码路径确认。

## 条件汇聚和并行汇聚为什么不同

| 场景 | 执行关系 | 正确等待方式 |
| --- | --- | --- |
| 并行检索 A 和 B 后汇总 C | A、B 都应执行。 | C 等 A、B 都完成，使用多来源 fan-in。 |
| 意图路由只选 A 或 B，再进入 C | A、B 通常只执行一个。 | 选中的分支完成即可继续，不能等另一个。 |

如果把条件分支当成并行汇聚，可能一直等待未被选择的节点；如果把真正并行当成独立来源触发，可能提前汇总或触发多次。

当前编译逻辑检查汇聚来源是否直接属于条件边的目标，并据此选择边类型。这解决已有配置中的两类汇聚，但不是任意嵌套条件、跨层分支的完整静态分析算法。复杂拓扑需要额外验证，不能只凭支持条件边就声称覆盖所有 DAG 结构。

## 变量和并行状态怎样处理

节点从 WorkflowState 读取输入和上游变量，输出更新共享状态。字典状态通过 reducer 合并，节点结果列表追加。开始节点声明形成工具输入参数，结束节点组织最终 outputs。

当前字典 reducer 使用合并覆盖语义。同一键被并行分支写入时，不能声称框架自动解决业务冲突；应该通过变量命名和引用设计避免冲突，必要时新增明确的聚合节点或冲突规则。

## 工作流为什么可以作为 Agent 工具

Workflow 继承 BaseTool，name 与 description 说明工具用途；_build_args_schema 根据开始节点变量动态创建 Pydantic 参数模型。模型提出工具调用后，参数进入工作流 inputs，图执行完成后返回 outputs。

这使固定步骤封装成一个复用能力，Agent 决定何时调用，工作流控制内部节点依赖。不能据此宣称整个 Agent 执行也变成完全确定性的流程。

## 典型追问与回答要点

**为什么草稿和发布配置要分开？**

用户调试中的半成品不应立即改变已发布能力。调试使用草稿，发布做校验并保存正式配置；实际版本回退能力应按对应服务确认，不能把所有应用能力都套到工作流。

**哪里做校验，哪里做执行？**

HTTP Schema 负责请求结构，Service 校验业务资源与权限，WorkflowConfig 校验图对象关系，节点负责具体执行。前端校验只帮助交互，后端仍要验证传入图。

**stream 是逐 token 还是逐节点？**

当前 Workflow.stream 调用图 stream，重点输出节点执行结果和状态，不应把它直接描述为与 Agent 工作台完全相同的 token 级事件协议。

**为什么还需要可视化工作流，Agent 不能自己规划吗？**

固定流程需要稳定的依赖、显式变量和可调试节点；开放任务需要动态工具选择。平台将工作流工具化，使两类执行方式组合。

**复杂嵌套分支如何进一步支持？**

可以增加显式汇聚策略、拓扑分析与分支完成标识，但这属于后续设计。先解释现有直接条件目标识别的边界，不把设想说成实现。
