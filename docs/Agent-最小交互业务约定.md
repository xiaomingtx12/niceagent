# Agent 最小交互业务约定

确认日期：2026-09-15。状态：用户已确认的目标行为，尚未据此完成代码改造。

实施进度：首批表单字段及取消重开流程已调整，见 [Agent Run 表单字段调整](Agent-Run表单字段调整.md)；数据库尚未迁移，完整业务验收尚未完成。

本文是 Agent 会话交互的业务依据。后续前后端实现、接口和字段设计均以本文为准；旧业务文档、API 文档及当前代码中的不同做法属于待对齐内容，不代表本约定已经实现。变更交互规则时先更新本文，再同步实现和相关说明。

## 1. 范围与基本概念

最小流程：**发送 → 执行 → 必要时调用 `ask_user` 等待填写 → 提交后恢复 → 完成。用户可以停止本轮，停止成功后在同一会话发送新一轮。**

| 概念 | 本文使用的含义 |
| --- | --- |
| 会话（Conversation） | 持续交流的容器，保存归属和历史；可以包含多轮问答，一轮结束不会结束会话。 |
| 一轮问答 | 一次普通输入及其处理结果，包含期间的表单补充、回答和累计用量。`ConversationTurn`（原 `Message`）记录表达这一轮，不等于前端的一条聊天气泡。 |
| 本轮执行（Run） | 完成本轮要求的逻辑运行；调用 `ask_user` 暂停后继续使用同一个 Run。 |
| 执行片段 | 启动或恢复到下一次暂停或结束之间的执行；恢复时分配新的执行标识，不改变 Run 身份。 |
| 表单批次（Input Batch） | 当前必须一起回答的一组待填表单。一次 Run 可以先后产生多个批次。 |
| 已接受提交（Submission） | 系统已经接受的一批答案及其回执；重复请求不能重复恢复执行。 |

页面上的“任务”可能指整个会话；讨论接口和数据时使用“会话”与“本轮执行”区分范围。数据结构现已定案为 `ConversationTurn + AgentExecution` 五表方案，见 [会话与执行表定案](Agent-会话与执行表定案.md)；协议中的 Run 对应 AgentExecution，不使用 AgentTask 命名。

同一会话同时最多有一个执行中、停止中或等待填写的 Run，跨入口访问也遵守这一占用规则。身份、应用归属和入口权限仍按现有授权边界校验。

## 2. 正常流程

1. 用户选择 Agent，打开已有会话或创建新会话，查看历史和当前状态。
2. 用户输入要求，可携带受支持的图片或附件；服务端接受后创建本轮记录并开始执行。
3. 页面展示流式输出和必要的工具过程。用户可以编辑下一条输入，但执行中不提交普通追加消息，也不排队等待自动发送。
4. Agent 调用 `ask_user` 时，系统保存中断及待填表单，进入“等待填写”。此时没有执行片段占用线程等待用户操作，但本轮仍占用会话。
5. 用户填写并提交当前批次的全部表单。校验通过且首次接受后，从原中断位置恢复同一个 Run，不新增一轮、不覆盖原始问题。
6. 后续再次调用 `ask_user` 时，重复步骤 4、5；新问题构成新批次，前一批已接受答案保持不变。
7. 完成后保存回答与累计用量，释放会话占用。用户再发送普通消息时创建新一轮。

示例：

```text
会话 C1
  第一轮 R1：分析销售报表
    读取文件 → ask_user 询问月份 → 提交“八月”
    继续分析 → ask_user 询问统计口径 → 提交口径
    继续执行 → 输出报告 → 完成
  第二轮 R2：与去年同期对比
    使用会话历史 → 输出对比 → 完成
```

Agent 主动使用 `ask_user` 的提问必须按表单中断处理，不能为了简化实现而改成“结束本轮、让用户另发普通消息”。

## 3. 状态和允许的操作

| 当前状态 | 普通消息发送 | 表单提交 | 停止 | 后续行为 |
| --- | --- | --- | --- | --- |
| 会话空闲 | 允许 | 没有可提交表单 | 无活动执行可停止 | 接受新输入后开始新 Run。 |
| 执行中 `running` | 不允许；可编辑草稿 | 没有当前待填批次时不接受 | 允许 | 完成、失败、进入等待填写，或处理停止请求。 |
| 等待填写 `waiting_input` | 不允许 | 接受当前批次 | 允许 | 接受答案后恢复原 Run；停止则结束本轮。 |
| 正在停止 | 不允许 | 不接受新的表单提交 | 重复操作不产生额外执行 | 等待执行退出及中断处置完成，再开放发送。 |
| 已完成 `completed` | 允许新一轮 | 仅可查询此前已接受提交的回执 | 不改变已结束状态 | 原 Run 保持终态。 |
| 已停止 `cancelled` | 允许新一轮 | 旧未提交表单失效；已接受提交只返回原回执 | 不改变已结束状态 | 原 Run 保持终态。 |
| 执行失败 `failed` | 允许新一轮 | 不接受新的表单答案 | 不改变已结束状态 | 原 Run 保持终态。 |

“会话空闲”是可开始下一轮的界面状态；“正在停止”由取消请求及真实执行状态表达，本文不要求增加两个数据库状态值。

停止请求与完成、表单提交并发时，由服务端串行判定生效结果：已完成的 Run 不被迟到停止改成取消；答案若先被接受，停止针对恢复后的执行；停止若先生效，未接受的答案不能复活该 Run。页面依据服务端结果展示。

## 4. 停止和修改要求

停止的含义是**结束本轮**，不是暂存一段可以以后恢复的执行。

- 执行中点击停止：显示“正在停止”，直到服务端确认执行退出并释放会话占用；不能只断开 SSE 就显示“已停止”。
- 等待填写时点击停止：废弃本批未提交表单，结束本轮；已经保存的输出、过程和已接受答案保留为历史。
- 页面已有待填表单和对应运行摘要时，停止直接使用该 Run ID；缺失时才补读会话状态。停止是否生效仍由服务端确认，成功后更新页面状态。
- 停止成功后：留在原会话，允许用户修改或补充要求，再手动发送新一轮。
- 原 Run 的已停止状态不可重新进入等待填写或执行中；页面不提供“重新填写并恢复”，旧客户端的重开请求也不能恢复它。
- 停止不撤销已经完成的工具副作用，不承诺立即中断不可取消的工具调用。
- 停止失败或尚未完成时，展示真实状态，允许查询或重试停止；不提前启动下一轮。

取消表单后，必须妥善处置图中遗留的中断，让新一轮可以正常开始且保留可用会话历史。仅改 Run 状态、删除表单展示，或要求用户新建会话绕过中断，都不满足本约定。具体 checkpoint 处置方式由实现设计确定。

## 5. 表单校验、重复请求与恢复

普通启动命令固定使用 `params.input.messages`，每条用户消息必须携带非空 `id`。同一次输入的网络重试沿用该 ID，相同 ID 携带不同输入会被拒绝；外层命令 `id` 仅关联响应。工作台在当前页面内保留未确认请求的消息 ID，服务端确认接受后才释放，主动修改输入视为新请求。`input.reopen` 不再属于可接受的命令。

- 页面提交的是当前批次全部待填表单。字段校验失败时保留填写内容，定位错误，保持等待填写，不启动执行。
- 刷新或重新进入会话后，应能重新取得同一待填批次。已提交答案可恢复展示；尚未提交的本地草稿不要求由服务端跨设备保存。
- 相同批次、相同已接受答案的重复请求返回原接受回执，不重复创建执行片段、不重复累计用量。
- 同批次答案接受后不可修改；不同答案的重复提交应拒绝。已经取消或过期且未被接受的批次不能提交。
- 重复请求返回历史回执不代表 Run 当前仍在执行；展示当前状态时以服务端的当前记录为准。
- 表单提交网络失败时保留填写内容；重试通过已接受记录判断是否执行过，不能仅凭客户端按钮状态判断。
- 恢复时重新校验权限和必要的运行条件。无法恢复时返回明确原因，保留可查看记录，并允许用户停止该轮后发起新一轮。

## 6. 输出、刷新和异常

| 情况 | 约定 |
| --- | --- |
| 正常完成 | 保存本轮回答、生成结果引用和累计用量；可以继续新一轮。 |
| 中途暂停 | 保存已产生的结果和本片段用量，待填表单保持可恢复。 |
| 失败或停止 | 保留已保存的部分输出并标记结果状态；重新发起属于新一轮。 |
| 页面刷新、切换会话或关闭页面 | 不主动取消后台执行；重新进入后查询真实状态，读取已保存内容并连接仍在执行的事件流。 |
| 网络断开、发送结果不明 | 查询或重试同一次请求以确认接受结果，不自动创建重复执行。 |
| 服务进程异常退出 | 识别失联执行并收敛为明确状态，不长期假装仍在运行，也不承诺自动从原步骤重跑；已持久化的有效等待表单按正常恢复校验处理。 |

执行过程查询和已持久化事件续传继续保留；本次业务精简不意味着删掉文本过程或事件序号。界面恢复不等于崩溃后自动恢复执行。

执行过程区以真实事件展示阶段：模型请求发起即出现调用记录，不等待首个 Token；收到公开的思考、正文或工具内容块后，更新为思考、生成回答或准备工具，工具开始后展示实际执行及结果。模型开始与结束沿用现有事件表和 custom 通道，每个调用只增加两条轻量边界事件，不保存提示词或参数分片，也不新增持久化快照。模型调用身份用于合并请求进度与消息流，恢复重放不能产生重复记录；底部不增加调用次数统计。摘要生成仍作为独立的上下文整理阶段，供应商内部 HTTP 重试次数不据此推算。旧记录没有保存的请求起点不补造。

### 6.1 实时展示、保存和统一恢复约定

运行中的公开事件先通过内存实时发送，再由独立写入线程批量保存，不等待数据库提交才显示。实时事件和保存事件共用同一序号，不另建消息表、缓存表或持久化展示快照。写入队列和实时尾部有界；数据库持续跟不上时限制生产速度，不能无限占用内存。

正常完成、等待填写和主动停止前，先排空已发布事件的写入队列，再原子保存最终回答、用量、表单和执行状态，提交成功后才发送最终状态。正文已显示完不等于本轮已经保存完成；写入失败不能宣告成功完成。服务进程异常退出时，允许丢失最后一小段已显示但未保存的内容；重启后以已保存记录恢复，不承诺这段内容仍然存在。

浏览器刷新与网络重连共用下面的恢复流程。只要服务进程仍正常运行，尚未落库的内容从短期内存尾部补齐；客户端变慢、历史超出内存保留范围时，先从数据库追平到内存覆盖范围，再继续实时接收。

SSE 正常结束订阅后发送 `: stream-end` 注释，异常退出不发送。前端用短尾部识别该注释，将缺少结束标记的 EOF 交给 SDK 有限重试；不再为观察连接状态重复解析快照和增量 JSON。该注释不分配事件序号、不落库，也不表示 Run 成功，运行结果仍由根生命周期或恢复快照确认。

- 正常连接继续流式展示。断线后由客户端自动重连，显示“正在恢复最新进度”；有限重试失败后明确提示刷新重试，不将连接失败当作执行完成或停止。
- 每次连接先获取本轮截至已提交水位 S 的完整展示材料，再接收序号大于 S 的内存尾部及新事件，补齐阶段正文、思考内容、工具过程、当前表单及执行状态。已提交水位只用于恢复，不限制实时交付；断线期间的内容直接显示，不按原速度重播打字动画。
- 展示材料与水位由服务端配套生成。构造期间新增的事件仍通过后续 SSE 发送；客户端按 Run 和水位替换旧过程、忽略重复前缀并保留已收到的新事件，不能用刚收到但尚未应用的网络字节游标跳过内容。
- 刷新后先查询会话状态。仍在执行的 Run 建立上述 SSE 连接；已结束或等待填写的历史过程按需读取一次完整展示材料，不自动循环请求原始事件分页，也不显示按 Token 分页的“加载更多”。会话旧问答分页保持独立。
- 会话状态中的问答、运行摘要与最新展示状态读取同一个已提交数据库快照，避免出现已完成状态配上提交前的空回答。初始化保留最近 20 轮问答；历史执行只取摘要，完整展示状态和表单仅从最新 Run 读取。
- 同一会话发送新消息不能清空已展示的历史。当前执行的恢复材料或图状态可能只包含部分消息，客户端按消息 ID 合并；重复绑定同一会话不重置历史缓存，真正切换会话时才清空。
- 会话订阅与单次 SSE 连接分别管理。每次新一轮命令或表单恢复命令被接受后，都为该次执行建立 SSE；表单恢复即使沿用原 Run ID，也不能复用已结束的连接。完成或等待填写时关闭本次连接，会话订阅继续等待下一次执行；空闲期间不轮询、不重复连接已结束的 Run，切换会话或离开页面时释放旧订阅。
- 保留全部已持久化且对当前用户公开的阶段及工具记录。恢复后的过程可查看，恢复前的逐 Token 动画和原始时间间隔不重演；未落库或未公开的内部信息不属于恢复承诺。

实现协议：工作台发送 `recovery: "snapshot"`，SSE 首帧为 `workbench.snapshot`，包含 `run_id`、`sequence`、`run`、`values` 和合并后的 `events`。历史详情使用 `GET /agent-runs/{run_id}/snapshot`，沿用会话归属校验；旧 `/events` 分页和不带 recovery 的游标订阅保留兼容。

此处快照是按需计算的连接响应，不是新的持久化字段，也不是 Agent 恢复执行使用的 checkpoint。同一模型内容块的文本增量合并为整段，调用身份、边界、工具事件及原始落库数据保留。当前实现需要服务端按序扫描本轮原始事件；大幅减少的是客户端事件重放和分页请求，不承诺超长执行的快照生成耗时恒定。本次不引入缓存表或额外持久化投影。

工作台不展示工具参数逐字符生成的过程。当前协议的工具参数 `content-block-delta`（`delta.type=block-delta` 且 `delta.fields.type` 为工具类型）在分配平台事件序号之前过滤，不进入事件表或 SSE；正文和内容块起点已实时发布，不等待后续参数分片。工具参数的完整内容块结束事件、工具开始时的完整输入、执行结果和错误继续保存，正文、思考过程、消息边界、用量及当前协议的其他内容类型保留。Agent 内部消息及 checkpoint 不受这层展示过滤影响。

历史快照按同一展示规则在数据库查询中排除标准工具参数分片，再读取其余载荷。实时和历史统一使用当前 langchain-protocol：起止事件读取 content，增量事件读取 delta；不再兼容旧 content 增量、缺失起点或未知增量格式。本次不改写已有事件行，历史恢复只支持当前格式。SSE 快照与历史详情共用过滤规则，长历史仍有扫描成本。

耗时与用量按执行片段累计一次；等待用户填写的时间不计入执行耗时，重复结算不能重复累计。回答、状态、用量和对应事件需要一致提交，页面只能将已确认的结果当作完成。

### 6.2 异步子 Agent 的后台任务展示

异步子 Agent 在独立会话和 Run 中执行，启动成功只代表已接受任务。父 Run 的完成、停止或流式连接关闭，不能据此判断子 Run 的结果，也不等待父事件流出现子任务正文。

工作台从会话状态的 `async_tasks` 恢复清单，结合已加载的实时任务记录按任务标识去重，在工作台顶部提供“后台任务”入口；无需展开父 Run 的历史，也不占用聊天正文区域。当前账号有权读取的本平台子 Run 每 3 秒批量确认一次状态，每批最多 50 个，仅查询尚未结束的任务；页面隐藏时暂停，回到前台恢复，离开会话释放请求。完成、失败、停止后结束轮询，等待填写仍需继续确认。

后台任务侧栏进入会话时保持关闭，只由用户点击打开；状态确认、任务结束和新任务到达均不自动开关，避免初始化先展开再折叠。顶部入口保留总数、运行中标识和失败或状态读取错误提示。侧栏优先展示最近加入的任务，支持全部、未结束或待确认、已结束筛选，每次显示 30 条，用户点击后继续显示；返回清单保留筛选与已显示数量。

每个任务统一使用“查看详情”，在同一侧栏内先展示已保存回答，下方折叠的执行过程由用户展开时读取子 Run 的恢复快照，不叠加第二个侧栏。任务未结束时明确说明这是本次读取的已保存内容，结果与过程允许手动刷新；返回清单、关闭侧栏或切换会话时取消详情请求，迟到响应不覆盖新选择。状态请求失败展示错误并提供重试，不凭浏览器计时或父图中的启动快照假装持续运行；外部或不可访问的任务明确标为状态不可用。详情查询与轮询并发时，已确认终态不能回退。

这一步只完成工作台的状态与结果展示，不更新父图的 `async_tasks`，不自动恢复父 Agent 汇总结果，也不提供全站通知或子任务表单提交入口。

## 7. 实现范围和待对齐事项

保留：多轮会话、附件、模型与工具调用、流式输出、执行过程、历史、用量、停止、`ask_user` 暂停恢复、刷新恢复展示和重复提交保护。

本版不包含：运行中注入普通聊天消息、会话内多轮并行或自动排队、停止后恢复原 Run、取消表单后重开、服务崩溃后自动续跑，以及同一轮多个独立生成版本。

以下是当前实现与目标的对齐事项，不表示本次文档修改已经完成这些改造：

| 当前实现位置或行为 | 需要对齐的目标 |
| --- | --- |
| `input.reopen`、`reopen_form`、前端“重新填写”入口 | 退出取消重开流程；兼容旧请求时也只能返回已停止或不支持，不能复活原 Run。 |
| `cancelled_inputs`、`input_recovery`、取消与重开序号 | 随取消重开流程评估移除；必要历史通过现有记录保留，不维持可恢复副本。 |
| 取消待填后阻止普通新消息，提示新建会话 | 完成中断处置后允许原会话开启新一轮。 |
| 当前三块 Run JSON | 调用参数服务于恢复；交互数据服务于当前表单及必要历史；展示快照仅保留页面需要的投影。不能因字段名笼统就全部删除，也不复制完整 checkpoint。 |
| `input_history` | 当前模型装配还会读取问答语义，精简前明确其替代来源；仅有答案的 Submission 不能自动替代完整问题上下文。 |
| 不同调用入口及内部 SDK 的重启行为 | 共用会话占用、停止生效和终态规则；已有“先停止再新建”的适配不解释为向原 Run 注入新消息。 |

表名和职责按 [会话与执行表定案](Agent-会话与执行表定案.md) 执行；配置版本方案和多进程执行架构不在本次改造范围内。

## 8. 实现验收场景

1. 普通输入完成后，在同一会话发送第二个问题，创建新一轮且能使用会话历史。
2. `ask_user` 展示表单；填写后恢复原 Run；一轮连续出现两批表单也不改变本轮身份。
3. 表单字段无效、部分表单未提交时保留草稿并提示错误，执行保持暂停。
4. 相同批次相同答案重复提交只恢复一次；不同答案不能覆盖已接受内容。
5. 运行中或等待填写时不能直接发送普通新问题；跨入口请求也不能绕过会话占用。
6. 执行中停止，确认退出后才开放发送；重复点击停止不改变已完成结果或启动额外执行。
7. 等待表单时停止，旧表单失效且不能重开；原会话可以发送新问题，旧 checkpoint 中断不会再次阻塞。
8. 停止与提交、停止与完成并发时按服务端生效顺序处理，旧请求和旧执行片段不会复活或覆盖已结束的 Run。
9. 刷新等待填写的页面仍展示原批次；刷新执行中的页面不重复启动，能恢复内容及执行状态。
10. 中途失败、服务异常后展示真实结果，保留已保存内容；用户重新发起新一轮不重复计入旧片段用量。
11. 长输出中断网，后台继续到接近完成或已经完成：恢复后补齐阶段正文和工具过程，无重复回答、不循环追赶事件分页；快照水位之后的增量继续显示。
12. 生成恢复材料期间继续产出事件、连续两次断线、恢复时切换会话：不丢增量、不回退到旧状态、不将旧会话过程带入新会话。

这些场景用于前后端联调与功能验收，不要求另建自动化测试文件。
