# ⑨ 恢复、持久化与后台执行：三份状态各管什么

[返回组件地图](00-组件地图.md) · 业务链路见 [后台执行、部署与排障](../platform/implementation/11-后台执行部署与排障.md)

## 这块组件在干什么

排障时先问：你看着的是哪一份事实？

| 来源 | 存什么 | 谁写 |
|---|---|---|
| 业务表 AgentExecution | 对用户可见的状态、待填、用量、executor_id | Service 结算 |
| LangGraph checkpoint | 图能不能 resume 的执行状态 | Checkpointer |
| 进程内 Tracker / Hub / Event | 本机是否还握着这个片段 | 当前 Web 进程 |

用内存 Tracker 推断别的进程上的 Run，会误杀。用 checkpoint 当业务终态，会和页面不一致。

## 当前怎么做

### Checkpoint 与 Store

`AGENT_CHECKPOINT_BACKEND` / `AGENT_MEMORY_BACKEND` 默认 postgres。Saver 对瞬时断连重试一次。连接池独立于 Flask SQLAlchemy 池（checkpoint max 5，memory max 2，`MAX_WAITING=0` 表示不等待空闲连接）。构造失败必须关池。进程共享，不随单次 Run close。

thread_id = `conversation_id`。恢复时新执行器、同一 Checkpointer、新 `executor_id`。

### 执行资格

片段开始时把 `executor_id` 写到行上；结算成功后清空。行上已有 executor_id 时不能再 acquire。取消请求记在旧片段上，新片段 acquire 时清掉，避免旧取消挡住恢复。

`_lock_execution` 用 `FOR UPDATE` 且校验 executor_id + 活动状态，迟到线程写不进去。

### 孤儿

`_settle_orphan_runs` 把「活动状态 且 不在本进程 Tracker」的行收敛掉。这是**单进程假设**下的回收。多 worker 时另一个进程的健康 Run 会被当成孤儿——文档和代码都把跨机租约写成后续项，不是现状。

### 任务跑在哪

| 任务 | 哪里跑 |
|---|---|
| 主 Agent Run | Web 进程内 ThreadPoolExecutor（默认 5）+ BoundedSemaphore |
| 本平台异步子 Agent | 内部 HTTP 再创建 Run，仍进上述池 |
| 文档索引启停删 | Celery |
| Agent 测评 | Celery |
| 事件合批写库 | 每个活动片段独占写线程 |

把 `execute` 包成 Celery task **不够**迁移：还要租约、过期回收、幂等重投、跨进程取消、事件通知、Worker 退出时的资源。写工具也不能因 Worker 重投无限重放。

线程执行自建 Flask context 和 Session；模型调用前尽量结束读事务。业务库、checkpoint、Store 的空闲要分开看。

## 明确不保证

- 进程挂了，另一台机器不会认领 checkpoint 接着跑
- SSE 打到别的进程时，读不到原进程内存尾部（只能靠已落库前缀）
- 没有金额/墙钟硬预算；没有跨 resume 的总步数预算
- checkpoint 池 `MAX_WAITING=0`，并发高时直接拿不到连接
