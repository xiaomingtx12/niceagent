# ⑦ 工作区、沙箱与文件交付：副本何时变成已保存文件

[返回组件地图](00-组件地图.md) · 业务链路见 [工作区、文件交付与执行环境](../platform/implementation/08-工作区文件交付与执行环境.md)

## 这块组件在干什么

`/workspace/` 是**本轮临时副本**。普通 write/edit 和 Shell 改副本，不会自动改平台已保存文件。用户要的交付物必须显式 `deliver_file`。装配时不下载全部历史文件。

## 当前怎么做

### 路径和工具

| 工具 | 行为 |
|---|---|
| `list_saved_files` | 只查已保存元数据 |
| `load_saved_file` | 按需拉一个文件进副本，记下真实 revision |
| `deliver_file` | 把指定产物写入 COS；成功才返回 saved 和 path |
| 原生 write/edit | 只改副本 |

持久化空间按账号+应用派生稳定 scope。表字段 `workspace_files.conversation_id` 存的是这个 scope，不是某个真实 Conversation。附件写入本轮副本，不自动进文件库。

配额默认：总 100MB、1000 个文件（`WORKSPACE_MAX_*`）。

### 覆盖冲突

revision 绑在「这份工作副本路径 + 保存目标」上。重复 load 同一来源不覆盖模型已经改过的副本。没 load 过的目标按 revision=0 只允许新增。另一个会话已保存新版本 → 本次 deliver 冲突，不强行覆盖。把新版本 load 到另一副本，旧副本不会因此获得覆盖权。

### COS 与元数据顺序

`write_bytes`：算摘要 → 用唯一 object key 上传 → 作用域锁内校验版本/配额/路径并提交元数据（revision++）→ 元数据失败则尽力删新对象；成功则尽力删旧对象。删除先让元数据不可见，再清对象，避免清理失败后用户还能从正常列表看到已删文件。

对象存储和 PostgreSQL **没有**分布式原子事务。best-effort 失败可能留下无引用对象，当前没有完整 GC。

### 沙箱

`AGENT_SANDBOX_PROVIDER` 默认 `disabled`。可选 Bubblewrap（Linux 本机隔离）、LangSmith、Daytona。远程 Provider 延迟初始化，第一次真正需要才建资源。本机 Shell 直接共用本轮目录；远程先用本地副本，启动时只迁移已加载/已生成文件，之后文件工具和 Shell 都走远程。

文件工具用虚拟路径 `/workspace/`、`/skills/`；Shell 从共同物理父目录启动，命令里要用 `workspace/` 相对路径，**不会**自动替换字符串里的虚拟绝对路径。Skill 授权包在沙箱里 `chmod a-w`。

资源关闭**不**扫描回写。取消、失败、waiting_input 之后，未 deliver 的文件不保证还在；恢复应重新 load 已保存输入并重建中间产物。

## 明确不保证

- 虚拟路径 ≠ 主机级进程隔离；安全能力取决于实际 Provider 和网络开关（默认沙箱禁网）
- 关闭运行不会把副本同步成已保存文件
- 无引用 COS 对象可能残留
