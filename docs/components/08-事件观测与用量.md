# ⑧ 事件、观测与用量：先实时、后落库

[返回组件地图](00-组件地图.md) · 业务链路见 [事件协议与前端流式体验](../platform/implementation/03-事件协议与前端流式体验.md)

## 这块组件在干什么

三层转换：

1. Core 把 LangGraph v3 流收成稳定 `AgentEvent`（JSON 兼容，业务不碰 AIMessageChunk）
2. `agent_protocol` 绑定消息 ID 和业务序号，投影公开通道
3. 前端用 messages / 过程 / 上下文 / 任务等视图渲染

公开通道：`messages`、`values`、`tools`、`lifecycle`、`custom`、`input.requested`。`seq` 是顺序，事件 ID 是身份，namespace 分子图。框架根图结束 **≠** 业务已提交成功。

## 当前怎么做

### Core 出口

`AgentEventNormalizer` 只适配有序 v3：过滤摘要、展开完整消息、保留原生消息边界。Core 不缓存正文，不把缺少原生结束事件的消息标成成功。ask_user 的 GraphInterrupt 不当成 tool-error 往外抛。摘要若在片段结束时相对开头变了，补一条压缩完成通知。

### 缓冲：实时早于持久化

`AgentExecutionEventBuffer.emit` 在锁内：先入待写队列，再发布到内存实时尾部。独立写线程合批落库。

| 机制 | 当前值 |
|---|---|
| 待写队列 | 最多 512，持续拥塞才背压生产者 |
| 合批 | 最多 128，未满最多等 ~250ms |
| 内存尾部 | 最近 2048 条 |
| 收尾 | `finish()` 排空写线程；失败批调用线程补写，再失败按失败结算 |

正常订阅不查库。订阅者落后超出尾部时回库补齐。扫描游标按已扫描序号前进，过滤不公开事件不卡住续传。

每个活动片段独占写线程和 Flask app context，**不**把请求线程的 Session 借给写线程。

### 用量

`PlatformAgentRunObserver` 用 Callback 累计模型/工具调用次数和 token。按调用 ID 去重；开始即计数，失败不回退次数。`usage_present=False`（供应商没返回）和实测零用量分开。n>1 时只取每组第一条 Generation，避免同一份响应级用量加多次。结束 `finish()` 后迟到回调不再计费。

不保存 Span、父子调用链、阶段、工具输出。业务 Run 的 `trace_id` 关联消息；`executor_id` 防重复结算。Turn 用量由各片段 `apply_usage()` 累加。

上下文观测里的 cache_read_ratio 是单次请求补充字段，不进入 Run 账本的计费决策。

## 明确不保证

- 进程骤停时，已经显示但尚未提交的尾部可能丢，不能说「看见了就能重放」
- 没有 Generation 级 promptVersion，Skill/提示词变更后精确回放要对配置指纹
- Observer 不够做「静默漂移」在线比对，工作台过程靠 `AgentExecutionEvent` 时间线
