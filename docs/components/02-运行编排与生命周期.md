# ② 运行编排：会话占用、幂等和后台投递

[返回组件地图](00-组件地图.md) · 业务链路见 [会话与运行生命周期](../platform/implementation/02-会话与运行生命周期.md)

## 这块组件在干什么

HTTP 请求只负责接单。真正把「一次用户提问」变成可查询、可恢复的 `AgentExecution` 的是 `AgentExecutionService`。Core 执行器不认识数据库 Run。

四个对象不要混：

| 对象 | 作用 |
|---|---|
| Conversation | 持续会话和访问归属 |
| ConversationTurn | 一次用户问题、最终回答、累计用量 |
| AgentExecution | 这轮任务的启动、等待、恢复、取消、结算 |
| executor_id | **当前执行片段**的写入资格；恢复可更换，Execution ID 不变 |

SSE 连接是观察通道。关连接 ≠ 取消任务；重连 ≠ 再开一轮。

## 当前怎么做

### 启动

`start_run` 顺序：

1. 先 `_settle_orphan_runs`（本进程已不再持有的活动记录）
2. 锁 Conversation，让同会话的启动检查与创建串行
3. `_check_duplicate_start`：有 `input_message_id` 才去重；同 ID 同输入返回原 Run，同 ID 不同入口拒绝
4. 占用检查：`running` 与 `waiting_input` 都占会话
5. 同一事务创建 Turn + Execution，**建行时就分配 executor_id**
6. 提交前登记进程内 Tracker，避免并发请求把新记录判成孤儿
7. **事务提交后**才 `_submit_execution`，后台读不到未提交行

没有 `input_message_id` 的调用不承诺去重。前端重新点击发送会生成新消息 ID。

### 表单恢复

`submit_answers`：先按批次 ID 查 `AgentExecutionSubmission`。已接受且答案相同 → 原回执；答案不同 → 拒绝修改。新提交才锁最新 Run，校验身份、定义指纹、本地执行已闲，然后：

- 保存 Submission + `input_history`
- 清空 `pending_inputs`
- 换新 `executor_id`，状态回到 `running`
- 提交后再 resume 同一 Execution、同一 Turn，不插第二条用户提问

配置指纹变了不能盲目接续旧中断。

### 取消与重启

活动执行：先记停止请求，再通知本机执行器 drain。没有执行线程的待填运行可以直接取消并清表单。**已取消的 Run 不可恢复**；下一条普通消息创建新 Run。

`restart_run`（内部 SDK）：先校验新输入（失败不影响旧 Run），再取消并最多等 10 秒释放，超时返回「未启动」。更新场景不再允许进表单。

### 后台与结算

默认 `AGENT_RUN_MAX_WORKERS=5`，另用同容量 `BoundedSemaphore` 非阻塞占名额，满了走失败，不往无界队列里藏。

`_finalize_run` 核对 `executor_id` 与活动状态后才写终态和用量。迟到的旧片段不能覆盖新片段。Turn 用量是各片段累加，不是最后一个模型调用覆盖整轮。

### 查询

`AgentExecutionQuery.get_state` 只给最近问答、Run 摘要、待填状态，不拉全部 token 事件。短只读 `REPEATABLE READ`，避免消息和运行状态来自两个时刻。

## 明确不保证

- Tracker / 取消 Event / 运行名额都在**当前 Web 进程**。多进程下「本机没线程」不能当成 Run 已死
- 前端重复点击若换了消息 ID，不会复用原 Run
- 发布配置变更后，旧 waiting_input 不能用新能力接着填
