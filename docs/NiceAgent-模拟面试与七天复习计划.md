## 一、准备三种长度的项目介绍

### 30 秒：投递沟通与面试开场

> 我独立开发了 NiceAgent，一个 AI Agent 开发与任务执行平台。早期基于 LangGraph 打通模型、RAG、工具、工作流和应用发布，后来升级到 DeepAgents，支持规划、多 Agent、Skills、长期记忆和沙箱文件交付。我重点解决运行状态与事件恢复、资源授权、沙箱生命周期和文件回写一致性，并在真实调试中持续改进协议和性能。

### 90 秒：展开职责和一个例子

先讲用户场景，再讲两阶段演进，最后选一个真实问题。建议使用“任务已结束但页面仍计时”，避免开场同时堆满十几个技术名词。

应包含四个要素：独立开发范围、采用框架的原因、平台补齐的机制、一个能追溯的结果。可以说使用 Codex 辅助，但要能解释你如何判断建议是否正确。

### 3 分钟：架构说明

按一次“查资料、等待用户补充、生成报告”的任务说明：

1. 用户选择应用，后端解析模型、工具、知识库、Skills 与子 Agent 配置。
2. 命令创建 Run，并确定输入去重和执行权，启动后台执行。
3. DeepAgents 使用原生规划与工具能力，平台负责资源路由与授权。
4. 事件落库后通知订阅者，前端按 Run 消费 SSE；断线后按游标补取。
5. 需要补充信息时 interrupt，恢复请求校验后使用 Command(resume)。
6. 文件任务按需使用远程沙箱，回写时检测变化与版本冲突。
7. 终态关闭流，历史状态可以恢复；失联任务有后台收敛机制。

不要让案例强行调用所有能力。简单问答可能不需要子 Agent、检索、沙箱或人工输入。

## 三、第二轮模拟：后端与执行可靠性，50 分钟

### 1. Conversation、Run、Message、Event 和 Checkpoint 为什么要分开？

先给每个对象一句职责，再举例：同一会话多次任务，每次任务多个事件；Checkpoint 还包含图的执行状态，不适合直接当产品历史接口。

追问：一个 Run 中等待用户输入是否属于失败？消息记录已存在能否证明图状态可恢复？最终回答写入和任务终态如何协调？

### 2. 用户连点两次发送，会发生什么？

应说明输入幂等标识、数据库唯一约束、事务竞争与已有结果返回。区分同一输入重复提交与两个不同输入同时启动，不要用前端禁用按钮代替后端保证。

追问：唯一键冲突后事务如何处理？waiting_input 与正在执行状态的约束为何不同？如果模型已调用外部工具，命令去重是否就保证了工具只执行一次？

### 3. 为什么事件先提交再通知？

要点：通知只负责唤醒；若先通知后提交，读取者可能看到空数据；持久事件支持重连补偿。本地通知丢失可以依赖后续读取发现已提交事件，但实时性受唤醒/轮询机制影响。

追问：数据库已提交但进程立即崩溃怎么办？多个 Worker 下本地 Condition 是否仍足够？你会选择 Redis Pub/Sub 还是 Stream，分别承担什么？后两项作为扩展方案讲。

### 4. SSE 收到 EOF，是否应该马上显示完成？

不能。正常终态后的 EOF 与网络意外关闭不同。先说明当前 Run 的业务状态，再解释重连和游标。结合真实 EOF bug：迭代器结束必须是持续状态，不能只唤醒当时等待的 next。

追问：还有缓冲事件没读完怎么办？终态回调为什么不应该再 hydrate 打断消费？新 Run 为什么不能沿用旧 run_id？

### 5. 取消任务是不是杀死线程？

应说取消请求、状态变更、执行过程观察取消、终态收敛和资源清理。已经在远端执行的工具未必能立即停止；不要承诺硬实时撤销所有副作用。

追问：用户发出取消后切换会话，旧响应怎样避免修改新页面？旧执行者恢复后如何避免继续写终态？

### 6. 进程挂了，为什么有 Checkpointer 还需要租约？

图状态和执行权是不同问题。心跳与 executor_id 用于识别当前拥有者和失联；状态收敛后旧执行者的写入需要校验。恢复图状态不自动解决外部写操作重复执行。

追问：120 秒租约是否说明最多只等 120 秒就完成收敛？应考虑扫描周期、排队与故障；不能给绝对 SLA。

### 7. ThreadPoolExecutor 为什么还需要接纳限制？

max_workers 限制运行线程，内部队列仍可能积压。应解释项目配合信号量控制占用，并在失败/完成路径释放。当前限制执行槽位，不代表控制了模型 Token 总预算和所有远端子任务成本。

追问：为什么还没有把完整 Agent 放进 Celery？要答运行定义重建、人工续跑、执行权、重复投递与取消协议，不能只说“以后换一下队列就行”。

### 8. 文件发生并发修改如何处理？

画用户编辑与沙箱回写的交错时序，说明摘要识别变化、预期版本检查和冲突返回。对象存储与数据库之间用补偿，不是同一事务。

追问：三个文件写成功两个怎么办？清理对象失败怎么办？如何升级为整份报告原子发布？最后一个作为未来设计。

## 四、第三轮模拟：Agent 工程与产品判断，50 分钟

| 问题 | 必须说清的机制 | 常见失分点 |
| --- | --- | --- |
| 多 Agent 一定优于单 Agent 吗？ | 独立子任务、上下文边界、协调成本、共享文件冲突 | 只说并行必然更快 |
| 为什么 todo 不能直接当调度任务？ | 计划描述与实际委派分开，原生 task 负责执行 | 将规划器描述成自研通用调度器 |
| Skills 和 Tool 的区别？ | Skill 是指令/脚本/资料包，Tool 是可调用接口；Skill 也受执行权限限制 | 把 Skill 挂载当作授权全部工具 |
| 子 Agent 如何限制权限？ | 模型、工具、技能明确装配，空工具集合也有语义 | 缺省继承父权限却声称最小权限 |
| Checkpoint、摘要、长期记忆区别？ | 恢复状态、控制上下文、保存跨会话信息 | 将摘要称作全部长期记忆 |
| 为什么选择分类文件记忆？ | 用户操作成本、原生文件能力、按需加载、并发保护；旧条目与兼容导入已删除 | 把删掉版本 UI 说成不要一致性 |
| 用户说“以后回答简洁”，如何真正记住？ | 模型查目录、读偏好、调用 write_file/edit_file；下一次模型调用刷新 | 把提示规则说成每轮自动总结或确定性提炼 |
| 换会话、换模型还能读到吗？ | 同账号同应用共享 namespace；PostgreSQL 持久化，内存模式重启丢失 | 把记忆绑到模型名，或称已经实现向量记忆 |
| 删除记忆后还可能出现原文吗？ | Store 文件与后续索引已移除，聊天历史和 Checkpoint 可能仍有原文 | 承诺全链路遗忘或自动清除历史 |
| 为什么相同维度 embedding 不能混用？ | 语义空间与模型指纹 | 只校验维度就说兼容 |
| 项目 full_text/hybrid 到底怎么实现？ | 说清当前关键词算法及合并方法，与 BM25/精排区别 | 背通用 RAG 流程却讲错当前实现 |
| Workflow 如何编译？ | DSL 校验、节点/引用/依赖、拓扑与 StateGraph | 声称支持任意循环与任意嵌套汇聚 |
| 代码节点和沙箱有何区别？ | 固定 Workflow 的 SCF 代码节点与工作台文件执行场景 | 把 AST 校验当作安全沙箱 |
| 模型目录返回模型就代表支持 tools 吗？ | 模型发现与能力证据分开，可选参数与显式覆盖 | 将 OpenAI-compatible 等同全部能力兼容 |
| 如何判断任务通过用户标准？ | Rubric、证据、候选绑定、修订上限、裁判局限 | 声称 LLM 裁判保证绝对正确 |
| 怎么定位运行慢？ | Run 关联、首字/模型/工具/摘要/沙箱/回写分段 | 将总耗时都归为模型或只看 Token |

最后追加一道产品题：**如果只能保留五个核心能力，你会怎么选？**

没有固定答案。应先明确目标用户和任务，再选择能力。例如面向复杂资料整理，可靠任务状态、检索/工具、文件交付、必要人工补充和结果校验可能更重要；不要脱离场景按技术热度排序。

## 五、4 道白板练习

### 白板 A：Run 级 SSE 时序，10 分钟

画客户端、命令服务、执行器、数据库、流读取五条生命线。标出 command 返回 run_id、事件事务提交、通知、since/Last-Event-ID、终态与 EOF。

随后用红笔加入：提交前连接断开、提交后通知丢失、终态前网络 EOF、页面切换到另一个会话。逐个解释谁负责恢复，哪些只是重读，哪些可能产生副作用。

**验收：** 游标必须有 Run 归属，业务终态和网络 EOF 分开；没有为了重连重新执行模型任务。

### 白板 B：人工输入与状态恢复，10 分钟

画 running→waiting_input→恢复执行→终态。旁边标注 Checkpoint、待回答表单 ID、恢复输入、身份校验、去重和配置来源。

追加两种竞争：重复提交答案；用户重新打开表单后提交旧答案。说明如何识别当前输入，不要只说保存一个布尔值。

**验收：** 不需要 HTTP 请求一直等待用户；能解释恢复时哪些代码可能重新进入，以及外部副作用为什么需要独立保护。

### 白板 C：沙箱与文件一致性，12 分钟

画持久工作区与沙箱两侧，起点文件 revision=5。执行期间用户将文件改到 revision=6，沙箱基于 revision=5 产出新内容，再回写。

追加远程创建成功但登记失败、TTL 到期、旧句柄释放、上传 Skills 中途失败。解释清理责任和错误出口。

**验收：** 不覆盖 revision=6；租约与 generation 的作用明确；承认多文件不是全局原子提交。

### 白板 D：从单进程扩到多 Worker，15 分钟

这是未来设计题。列出当前进程内状态：执行接纳、通知、沙箱池及相关本地缓存；决定哪些可以每个 Worker 独立持有，哪些需要全局协调。

设计任务持久化输入、Worker 执行权、过期扫描、跨进程通知、工具幂等和资源配额。说明你会先改哪个点以及如何验证。

**验收：** 不把加 Gunicorn worker 数或换 Celery 当作全部方案；数据库仍保存可恢复事实，消息系统和资源池有明确职责。

## 六、评分方式与改进顺序

每项 0～4 分，总分 24。该评分用于自练，不能预测录用结果。

| 维度 | 0～1 分 | 2 分 | 3～4 分 |
| --- | --- | --- | --- |
| 问题表达 | 只有技术名词 | 能说需求与症状 | 能用真实时序说明为什么困难 |
| 机制理解 | 把能力归给错误组件 | 说明主流程 | 能解释事务、状态、权限与资源边界 |
| 证据可信度 | 编造指标或事故 | 有案例无范围 | 能对应提交并说明测量/联调范围 |
| 方案取舍 | 只说最终方案好 | 有一个对照方案 | 能区分试过、讨论、延后并解释代价 |
| 追问应对 | 重复原话 | 能回答一层 | 能处理竞争与失败路径，承认不确定 |
| 表达结构 | 长篇散讲 | 结论与机制基本清楚 | 能在 30 秒/2 分钟间调整深度 |

建议目标：总分达到 18 且无明显事实错误，再扩展难题。若机制不清，先回源码；若案例不真实，回历史证据；若只是表达冗长，练习删掉类名和无关背景。

每次模拟后只记录三个问题：今天讲错的事实、讲不清的时序、需要补证据的结论。下次先复测这三项。
