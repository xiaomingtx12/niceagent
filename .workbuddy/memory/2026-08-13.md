## deepagents editable→普通安装（消除 IDE 报红）

### 背景
- IDE 中 `from deepagents.backends.protocol import (...)` 报红"未解析的引用 'deepagents'"
- 根因：venv 内 deepagents 为 PEP 660 editable 安装（site-packages 只有 `__editable__.deepagents-0.6.12.pth` + finder，无实体目录），JetBrains 静态索引无法解析 meta-path finder 映射
- editable 源码指向 `D:\open_code\ai-native\deepagents-main\libs\deepagents\deepagents`

### 修复
1. venv 卸载 editable 版：`pip uninstall deepagents`（需 unset CODEBUDDY_SESSION_ID/CLAUDE_SESSION_ID/CODEBUDDY_SAFE_DELETE_SANDBOX 绕过 sitecustomize safe-delete shim，否则删 .pth 报 SAFE_DELETE_FAIL_CLOSED）
2. 普通安装：`pip install deepagents==0.6.12 --no-deps` → 实体目录落位 `D:\spring_project\py\my-dify\.venv\Lib\site-packages\deepagents\`
3. 顺带修复 venv 两个残留空目录（命名空间包污染，`__file__` 为 None、pip list 无记录但 import "成功"）：
   - 空 `anyio/` → rmdir + `pip install anyio`（装 4.14.2），修 `No module named 'anyio.to_thread'`
   - 空 `anthropic/` → `pip install anthropic`（装 0.121.0，rmdir 权限拒绝但 pip 直接写入），修 `module 'anthropic' has no attribute 'DefaultHttpxClient'`

### 差异提示
- editable 源码版 graph.py 走 `langchain.agents`；PyPI wheel 版 graph.py 额外走 `langchain_anthropic`→`anthropic`，故普通安装后运行时 import 链路更长，才暴露了 anthropic 空目录残留
- 代价：失去对 `D:\open_code\ai-native\deepagents-main` 源码的实时修改能力

### 验证
- `from deepagents.backends.protocol import (...)` 运行时 IMPORT OK，location 指向 venv site-packages，version 0.6.12
- IDE 报红应随实体目录就位而消除（需重建索引）

## DeepAgents 官方生产文档研读（going-to-production）

### 核心认知
- 官方"生产"答案是「deepagents 库 + LangSmith 托管平台」二合一：库只给本地积木（Backend/中间件/checkpoint/memory），身份认证、授权处理程序、RBAC、OAuth、密钥注入、Store、可观测性、定时任务都放在 LangSmith 平台层。
- my-dify 是自托管多租户平台，不能外包平台层 → 必须自建等价物（DenyBackend/RuntimeScope/路径 ACL/配额/审计/skill_execution 沙箱），这正是 04 文档各 Backend 适配器的由来。

### 官方硬结论（直接印证 my-dify 现有决策）
1. 不要在已部署 Agent 用 `FilesystemBackend` / `LocalShellBackend`（直接访问主机）。
2. 要执行代码必须用沙盒（如 DaytonaSandbox），文件系统后端不够。
3. 共享内存是提示注入向量，组织/助手级策略需强制只读（my-dify 的只读 memory profile 投影一致）。
4. 密钥不要通过 env/文件进沙盒，用认证代理或空环境（my-dify runner 的 `--clearenv` 一致）。
5. 多租户三件事必须自己做：验证身份、控制访问、管理代理凭证。
6. 内存持久化 = CompositeBackend 把 `/memories/` 路由到 StoreBackend，命名空间 (user_id,)。

### 对"为什么不直接用原生 VFS/权限"结论的修正
- 之前把"权限"只看成 FilesystemPermission（工具层文件路径规则）不完整。完整授权是三层：平台身份/资源所有权 → 工具层 FilesystemPermission → 数据层 Backend ACL。my-dify 无 LangSmith，三层均自实现。
